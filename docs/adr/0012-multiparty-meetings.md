# ADR-0012: 多人数の会議に対応し、話者の分類はしない

## ステータス

Accepted (2026-09-12)

## 背景

5人のチームで全員が常駐させている状況を想定する。ここまでの決定はいずれも2人を前提にしていた。

### 人数が増えるほど道具としての値打ちが上がる

要望書の中心にある困りごとは「ハードなのか、ソフトなのか、ネットワークなのか、切り分けが
できない」である。

**2人では、劣化が自分の側か相手の側かを判定できない。** どちらも片側からの記録しか持たないためで、
これは実装の不足ではなく情報の不足である。

5人なら**多数決で切り分く。** 4人全員が私を劣化として記録していれば私の側、1人だけならその人の側。
**2人では原理的に得られない情報が出る。** したがって多人数への対応は規模の話ではなく、
**要件の中心に効く。**

### 要望書の2つの目的は、必要な仕組みが違う

要望書は2つを求めている。**「指摘されずとも気づける」**と**「指摘されたら振り返れる」**である。
前者はその場で、後者は事後でよい。

**ローカルだけで検知できない行が1つある。**

| | ローカルだけで検知 | 要るもの |
|---|---|---|
| 自分のマイクが悪い | できる | なし |
| **自分の声が届いていない** | **できない** | 相手の聞こえが常時 |
| 相手の声が聞こえない | できる | なし |

真ん中の行が「聞き取りづらいと言われてるのに記録上は正常」そのものである。**そこだけが遠隔の
データを必要とし、頼んでから取りに行く形では間に合わない。** 頼んだ時点で、もう過ぎた話になる。

## 決定

### 1. 話者の分類はしない

声から誰かを判別するには周波数の情報が要る。広帯域の包絡1本ではできない。
**分類しようとした瞬間に[Bolthole](0010-recording-floor-broadband-only.md)を出ることになる。**
制約のほうが先に答えを出している。

### 2. 単独発話区間は各自がローカルに判定する

自分のマイクが鳴っていて、同時に**自分の聞こえが下限に張り付いていれば、その区間は自分が単独で
話していた**ことになる。他の誰かが話していれば、自分の聞こえにその声が出るからである。

**誰の声かを判別する必要はなく、誰の声も来ていないことが分かれば足りる。** 必要なのは自分の
2本だけで、他人の記録は要らない。

その区間では、相手全員の聞こえは自分の声だけを測っている。それが要望書の問いにそのまま答える。

### 3. 交換はpull型にする

単独発話区間は本人にしか分からない。したがって**「この区間の聞こえをください」と頼む形**にする。

返ってくるのは頼んだ本人の声から作った記録だけになる。[ADR-0009](0009-record-exchange-transport.md)で
「自分のマイク記録は外に出ない、渡すのは相手自身の声から作った記録」と整理した性質が、
**人数が増えても崩れない。** 5人でも2人と同じである。

加えて、求められたものしか送らないため「暗黙に送ることはNG」と構造的に噛み合う。
**押し付ける経路が存在しない。**

### 4. 同意は対を結ぶ時点で取り、会議中は継続して交換する

**「暗黙に送ることはNG」は、送信のたびに同意が要るという意味ではなく、同意なしに送らないという
意味と読む。** 対を結ぶときに一度明示的に同意し、その範囲で会議中は継続する。ビデオ会議で
参加した時点が同意であって、パケットごとに同意しないのと同じ構図である。

暗黙でないことを次で担保する。

- 対を結ぶのは明示的な操作で、指紋の突き合わせを伴う([ADR-0009](0009-record-exchange-transport.md))
- **交換していることが常時表示に出る。** 相手ごとの状態も出す
- いつでも切れる
- **会議アプリが鳴っている間だけ。** 終日ではない
- 送るのは[Bolthole](0010-recording-floor-broadband-only.md)の水準まで

### 5. 単独発話の印を出し、相手はその間だけ返す

自分が単独で話し始めたら**印を出す。** 相手は印が出ている間だけ、受信レベルを返す。

返ってくるのは**印を出した本人の声から作った記録だけ**なので、3のpull型と性質は変わらない。
**会議中に連続させた形にすぎない。**

返ってきたものを突き合わせる。

| 相手の返し方 | 判定 |
|---|---|
| 全員が下限 | **届いていない** |
| 全員が低い | 自分の側か上流 |
| 一人だけ低い | その人の側 |

**その場で通知する。** ここで要望書の「指摘されずとも気づける」が、自分のマイクの範囲を越えて
成立する。

なお**この応答がそのまま事後の記録になる。** pullは取りこぼしと詳細層の補充に使う。

### 6. アドレスの配布を共有の置き場に移す

ADR-0009は手渡しを採った。**5人では成立しない。**

| | 値 |
|---|---|
| 対の数 | 5×4/2 = 10 |
| 1人あたりの接続 | 4 |
| 1対の穴あけ成功率 | 70% |
| 10対すべて繋がる確率 | 0.7^10 ≈ **3%** |

再起動やネットワークの変更のたびに、各自が4人へ貼り直すことになる。ADR-0009は「貼り直しが
負担になってからランデブーへ移る」を判断点に置いたが、**5人を想定した時点で、運用を待たずに
設計の段階で到達している。**

**自前のランデブー(ADR-0009のイ)を置く。** 各エージェントが自分の名刺(現在のアドレスと公開鍵)を
預け、相手はそこから拾う。記録そのものは通らない。

同期する共有フォルダに置く案も検討したが、**同期の速さがものによる。** 5で会議中の常時交換を
持つと決めた以上、アドレスの配布も相応に速くなければならない。**数分遅れて届く経路では、
会議が始まってから繋がるまでが間に合わない。** pull型だけなら足りたが、常時を足したことで
要求が変わった。

なお全対が繋がらなくても壊滅しない。**繋がった相手の分だけ判定材料が増える**形で劣化する。

## 採用しなかった案

- **声で話者を分類する。** Boltholeを出る。上記のとおり制約が先に排除している。
- **各人の発話記録も交換し、それをマスクに使う。** 最初はこの形を考えたが、**他人の記録は
  要らない。** 自分の2本で足りる。交換する量と、記録を渡す相手の数が増えるだけになる。
- **多人数を対象外にする。** 原因の切り分けという要件の中心が、多人数でこそ満たせる。
  対象外にすると道具の値打ちが下がる。
- **アドレスの配布を共有フォルダに相乗りさせる。** 運用するサーバが増えない利点はあるが、
  同期の速さがものによる。常時交換の開始が遅れる。

## 影響

- 交換器が経路を2つ持つ。**会議中の常時**(印と応答)と、**事後のpull**(区間の要求と応答)。
- 常時表示に、交換中であることと相手ごとの状態を出す。同意が見えていることの担保でもある。
- **ADR-0009の経路の決定が変わる。** 「ア. 手渡し」を「イ. 自前のランデブー」に改訂する。
- 記録の形式は変わらない。[ADR-0006](0006-file-exchange-before-p2p.md)の荷物がそのまま使える。
- 常時表示に出す接続状態が、1相手ではなく人数分になる。

## 未検証の前提

- **自分の聞こえが下限に張り付くことが「誰も話していない」と一致するか。** 会議アプリが音を
  絞る挙動を挟むと崩れうる。実機で確かめる。
- **重なりを除いたあと、使える区間がどれだけ残るか。** 5人の会話で一人だけが話している時間の
  割合を測っていない。ここが小さいと、この設計全体が成り立たなくなる。
- **自分の声が相手に届くまでの遅れが、印と応答の対応づけにどれだけ効くか。** 数百ms程度の
  見込みで、[ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md)の整合で吸収できるはずだが、
  常時の判定では事後の突合より効きうる。
- **穴あけの成功率70%を10対に独立と見てよいか。** 同じ回線に複数人がいるなど、独立でない状況が
  ありうる。上の3%は目安であって精度のある数字ではない。

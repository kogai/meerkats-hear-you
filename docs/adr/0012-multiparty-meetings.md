# ADR-0012: 多人数の会議に対応し、話者の分類はしない

## ステータス

Proposed (2026-09-12)

## 背景

5人のチームで全員が常駐させている状況を想定する。ここまでの決定はいずれも2人を前提にしていた。

### 人数が増えるほど道具としての値打ちが上がる

要望書の中心にある困りごとは「ハードなのか、ソフトなのか、ネットワークなのか、切り分けが
できない」である。

**2人では、劣化が自分の側か相手の側かを判定できない。** どちらも片側からの記録しか持たないためで、
これは実装の不足ではなく情報の不足である。

5人なら**多数決で切り分く。** 4人全員が私を劣化として記録していれば私の側、1人だけならその人の側。
**2人では原理的に得られない情報が出る。** したがって多人数への対応は規模の話ではなく、
**要件の中心に効く。**

## 決定(提案)

### 1. 話者の分類はしない

声から誰かを判別するには周波数の情報が要る。広帯域の包絡1本ではできない。
**分類しようとした瞬間に[Bolthole](0010-recording-floor-broadband-only.md)を出ることになる。**
制約のほうが先に答えを出している。

### 2. 単独発話区間は各自がローカルに判定する

自分のマイクが鳴っていて、同時に**自分の聞こえが下限に張り付いていれば、その区間は自分が単独で
話していた**ことになる。他の誰かが話していれば、自分の聞こえにその声が出るからである。

**誰の声かを判別する必要はなく、誰の声も来ていないことが分かれば足りる。** 必要なのは自分の
2本だけで、他人の記録は要らない。

その区間では、相手全員の聞こえは自分の声だけを測っている。それが要望書の問いにそのまま答える。

### 3. 交換はpull型にする

単独発話区間は本人にしか分からない。したがって**「この区間の聞こえをください」と頼む形**にする。

返ってくるのは頼んだ本人の声から作った記録だけになる。[ADR-0009](0009-record-exchange-transport.md)で
「自分のマイク記録は外に出ない、渡すのは相手自身の声から作った記録」と整理した性質が、
**人数が増えても崩れない。** 5人でも2人と同じである。

加えて、求められたものしか送らないため「暗黙に送ることはNG」と構造的に噛み合う。
**押し付ける経路が存在しない。**

### 4. アドレスの配布を共有の置き場に移す

ADR-0009は手渡しを採った。**5人では成立しない。**

| | 値 |
|---|---|
| 対の数 | 5×4/2 = 10 |
| 1人あたりの接続 | 4 |
| 1対の穴あけ成功率 | 70% |
| 10対すべて繋がる確率 | 0.7^10 ≈ **3%** |

再起動やネットワークの変更のたびに、各自が4人へ貼り直すことになる。ADR-0009は「貼り直しが
負担になってからランデブーへ移る」を判断点に置いたが、**5人を想定した時点で、運用を待たずに
設計の段階で到達している。**

**同期する共有フォルダに置く形**を推す。各エージェントが自分の名刺(現在のアドレスと公開鍵)を
ファイルとして書き、全員のエージェントがそれを読む。**運用するサーバは増えず、APIの組み込みも
要らない。** チームであれば共有の置き場は既にあることが多く、2人だけの場合と条件が違う。

無ければ自前のランデブー(ADR-0009のイ)に落とす。

なお全対が繋がらなくても壊滅しない。**繋がった相手の分だけ判定材料が増える**形で劣化する。

## 採用しなかった案

- **声で話者を分類する。** Boltholeを出る。上記のとおり制約が先に排除している。
- **各人の発話記録も交換し、それをマスクに使う。** 最初はこの形を考えたが、**他人の記録は
  要らない。** 自分の2本で足りる。交換する量と、記録を渡す相手の数が増えるだけになる。
- **多人数を対象外にする。** 原因の切り分けという要件の中心が、多人数でこそ満たせる。
  対象外にすると道具の値打ちが下がる。

## 影響

- 交換器が**pull型**になる。要求(区間の一覧)と応答(その区間の聞こえ)の2つを持つ。
- **ADR-0009の経路の決定が変わる。** 合意されれば「ア. 手渡し」を「エ. 共有の置き場」に改訂する。
- 記録の形式は変わらない。[ADR-0006](0006-file-exchange-before-p2p.md)の荷物がそのまま使える。
- 常時表示に出す接続状態が、1相手ではなく人数分になる。

## 未検証の前提

- **自分の聞こえが下限に張り付くことが「誰も話していない」と一致するか。** 会議アプリが音を
  絞る挙動を挟むと崩れうる。実機で確かめる。
- **重なりを除いたあと、使える区間がどれだけ残るか。** 5人の会話で一人だけが話している時間の
  割合を測っていない。ここが小さいと、この設計全体が成り立たなくなる。
- **穴あけの成功率70%を10対に独立と見てよいか。** 同じ回線に複数人がいるなど、独立でない状況が
  ありうる。上の3%は目安であって精度のある数字ではない。

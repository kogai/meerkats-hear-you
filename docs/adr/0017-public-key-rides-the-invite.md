# ADR-0017: 公開鍵は招待コードで渡し、ランデブーには預けない

## ステータス

Accepted (2026-09-14)

## 背景

MeerkatsBurrow の最初の仕事は、[ADR-0012](0012-multiparty-meetings.md) 決定4の
**「対を結ぶ」**である。枠は決まっている。

- 対を結ぶのは明示的な操作で、**指紋の突き合わせを伴う**([ADR-0009](0009-record-exchange-transport.md))
- ランデブーが担うのは、互いの送信先(公開アドレス、ローカルアドレス、**および公開鍵**)の
  交換と、穴あけの開始を揃える同期(同上)
- 端から端までの暗号化を行い、鍵は CryptoKit(同上)

決めていないのは、**公開鍵がどの経路で相手に届くか**である。ADR-0009 は上のとおり
ランデブーに載せる前提で書き、そのうえでこう書いている。

> **ただし「暗号化した」だけでは、守りたい相手から守れない。** ランデブーが公開鍵を取り違えて
> 渡せば、そこで復号できてしまう。経路の暗号化は通りすがりには効くが、**鍵を仲介する当人には
> 効かない。**
>
> 埋めるには鍵の指紋を一度だけ人が突き合わせる必要がある。**ここは安く済む。** 同意フローとして
> 招待コードの手渡しがどのみち要るので、そこに指紋を載せればよい。

**指紋を載せられるなら、鍵そのものも載せられる。**

## 論点

招待コードは手渡しである。Slack の DM、チャット、口頭——どれにせよ**ランデブーを通らない経路**で
相手に届く。そこに何を載せるかで、必要な作業が変わる。

| 招待コードに載せるもの | ランデブーが配るもの | 人がすること |
|---|---|---|
| 指紋 | アドレス + **公開鍵** | 届いた鍵の指紋を、招待コードの指紋と突き合わせる |
| **公開鍵そのもの** | アドレスだけ | **何もしない** |

下の行では、鍵が手渡しの経路だけを通る。ランデブーは配らないので、取り違えようがない。
**突き合わせる作業は、そもそも要らなくなる。**

### 突き合わせは安くない

ADR-0009 は「ここは安く済む」と書いたが、**人がやる手順として見ると安くない。**

指紋の突き合わせは、**人が正しくやったときにだけ効く。** 面倒だと飛ばされ、飛ばされても
何も起きない(繋がってしまう)。つまり**省略が検出されない安全確認**であり、この種のものは
長期的にはやられなくなる。やられなくなったことにも気づけない。

対して、鍵を招待コードに載せる形は**人に何も要求しない。** 手順が無いので、飛ばされようがない。

### 招待コードは長くなる

Curve25519 の公開鍵は32バイト。Base64 で44文字、短い指紋(たとえば8バイト)なら12文字程度なので、
**招待コードは30文字強のびる。**

これは手で書き写すには長いが、**手で書き写す想定ではない。** 手渡しといっても実際は
チャットに貼るので、44文字でも120文字でも同じ操作である。口頭で伝えることはできなくなるが、
それは指紋方式でも同じで、指紋を口頭で伝えたあと鍵はランデブーから来る。

### 検査値を載せる

**長さの検査だけでは足りない。** 切れたコードは長さで捕まるが、1文字だけ書き損じたコードは
**同じ長さの別の鍵になって通ってしまう。** 通ると、繋がらない対ができて原因が分からない。
ADR-0009 が「黙って繋がらないことは特に悪い」と書いた形そのものになる。

したがって公開鍵のハッシュの先頭4バイトを添える。**これは事故しか捕まえない。**
値は鍵さえあれば誰でも計算し直せるので、鍵を差し替える者は検査値も一緒に付け替えられる。
捕まえられるのは貼り間違い、切れ、文字化けだけである。

**改竄を捕まえる手段は、この形式には置かない。** 上で指紋の突き合わせを外すと決めた以上、
招待コードが通る経路そのものを信頼することになる。検査値をどれだけ長くしてもそこは変わらない。

形式は目印 `meerkats1:` に base64url(公開鍵32バイト + 検査値4バイト)を続けたもので、
**全体で58文字**になる。目印の末尾の数字は形式の版で、変えるときはここを上げる。

## 決定

### 1. 招待コードに公開鍵そのものを載せる。ランデブーは鍵を配らない

ランデブーが担うのは**アドレスの交換と同期だけ**になる。ADR-0009 が挙げた3つの役割から、
公開鍵の交換が外れる。

これでランデブーの持つ力が減る。ADR-0009 の表はこう書き換わる。

| | ADR-0009 | この決定のあと |
|---|---|---|
| 止まったとき | 新規の接続ができない | 変わらない |
| 見えるもの | 誰と誰がいつ繋いだか、双方のIPアドレス | 変わらない |
| **できること** | **鍵を取り違えて渡せば復号できる** | **できない。鍵が通らない** |

### 2. 鍵は Curve25519 の鍵合意鍵をひとつ

`Curve25519.KeyAgreement` の鍵ペア1つを、身元と鍵合意の両方に使う。署名鍵を別に持たない。

**持つ理由が無いからである。** 署名が要るのは「この鍵は確かに本人のものだ」を第三者に示す場面だが、
鍵は手渡しで届いており、示す相手もいない。

### 3. ランデブーに預ける名刺は、アドレスと、それが誰のものかを指す値だけ

> **[ADR-0018](0018-per-pair-rendezvous-handle.md) により、この決定のうち
> 「名刺を引く値が公開鍵のハッシュである」部分は置き換わった。**
> 名刺の場所は**対ごとに共有秘密から導く**値になる。公開鍵のハッシュは、
> 手元で対の一覧を引くための識別子として残るが、外には出ない。
>
> 置き換えた理由は、この決定が**失効を不可能にしていた**ためである。識別子が鍵から
> 決まると全員に対して同じ1つの値になり、招待コードを受け取った者はそれをいつでも
> 計算できる。**対を切っても、切られた側は名刺を引き続けた。**
>
> **名刺に公開鍵を入れない、という下の判断は変わらない。**

名刺には公開鍵を入れない。代わりに**公開鍵から導いた識別子**を入れる。相手は招待コードで
得た鍵から同じ識別子を計算し、それで自分あての名刺を見つける。

識別子は公開鍵のハッシュにする。鍵そのものを置くのと違い、**ランデブーは識別子から鍵を
復元できない。** 誰と誰が繋いでいるかは見えるが(元々見えている)、鍵は見えない。

### 4. 指紋は残す。ただし**突き合わせのためではなく、表示のため**

指紋は要らなくならない。要るのは次の2つで、どちらも人が能動的に比べる作業ではない。

- **相手の一覧に出す。** どの鍵で誰と対になっているかが見えないと、切りたいときに切れない
- **変わったときに警告する。** ADR-0009 が「指紋が変わったことを表示で明示する」と決めたとおり

用途が変わるので、**読み上げやすさより、一覧で見分けやすさを優先する。**
具体の書き方(16進か、単語列か、短縮の長さ)はこの ADR では決めない。
[ADR-0012](0012-multiparty-meetings.md) が多人数を対象にしたので、一覧に5人並ぶ前提で
実装時に決める。

### 5. 対の保存は Trust On First Use。鍵が変わったら、対を作り直す

ADR-0009 の TOFU をそのまま採る。ただし**「変わったら警告して続ける」ではなく、
「変わったら対を切って、作り直させる」**にする。

鍵が変わるのは、機械を変えたか入れ直したかである。ADR-0009 が
「機械を変えたり入れ直したりすると対が失われ、やり直しになる」と書いたとおりで、
**やり直しが正しい挙動である。** 警告を出しつつ古い対で繋ぎ続けると、
警告を無視した人が、誰のものか分からない鍵と記録を交換することになる。

## 影響

- **ランデブーの実装が軽くなる。** 預かるのはアドレスと、それを引くための値だけで、
  **鍵の取り扱いが無い。** 引くための値が何になるかは
  [ADR-0018](0018-per-pair-rendezvous-handle.md) で変わったが、鍵を扱わない点は同じ
- 招待コードが30文字ほどのびる(実際の形式は58文字)
- **指紋の突き合わせという手順が、利用者の手順書から消える。** ADR-0009 の同意フローは
  「招待コードを渡す」「受け取って貼る」の2つだけになる
- 機械を変えたときの手順が明確になる。対が切れて、招待コードをもう一度渡す
- ADR-0009 の「守れる/守れない」の表は変わらない。守れるものが増えるのではなく、
  **守るために人がすることが減る**

## 検討した代替案

### 指紋を載せ、鍵はランデブーから配る(ADR-0009 の想定)

**採用しない。** 上に書いたとおり、省略が検出されない安全確認を手順に残すことになる。
招待コードという手渡しの経路が既にあるのに、そこを鍵に使わない理由が無い。

### 招待コードにも鍵を載せず、ランデブーを信頼する

**採用しない。** 記録は経路に載らないので中身は守られるが、鍵を仲介する当人には効かない、
という ADR-0009 の指摘がそのまま残る。自分で運用するサーバであっても、
**設計として信頼しなくてよい形にできるならそうする。**

### 署名鍵を別に持ち、名刺に署名する

名刺の改竄をランデブーが行えないようにする形。**採用しない。**

改竄されて困るのはアドレスだが、**間違ったアドレスに繋ぎにいっても、鍵合意が失敗して終わる。**
繋がらないことは表示に出る(ADR-0009)。可用性の問題であって秘密の問題ではなく、
ランデブーを止めるのと同じことしかできない。鍵を1つ増やす価値がない。

### 鍵が変わったら警告して、対は維持する

**採用しない。** 決定5に書いたとおり、警告を無視した人が誰のものか分からない鍵と
記録を交換することになる。**「気づける」ことが要件のツールで、気づかなくても進める道を
残す設計は筋が通らない。**

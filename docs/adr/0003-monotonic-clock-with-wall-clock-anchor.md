# ADR-0003: 記録は連続単調時計と定期的な実時刻アンカーで時刻を持つ

## ステータス

Accepted (2026-09-11)

## 背景

要望書は「発話と相手側の聞こえ方を突合出来るようにもしたほうがいいだろう」としている。突合は、
2台の別のMacがそれぞれ記録した時系列を並べる作業であり、時刻の共通基盤がなければ成立しない。

一方、単一マシン内の記録にも要件がある。実時刻(wall clock)はNTP同期の補正やスリープ復帰で
不連続に動きうるため、これだけを使うと記録の順序や区間長が壊れる場合がある。

突合の実装自体は後回しと決めている([ADR-0006](0006-file-exchange-before-p2p.md))。しかし時刻の
持ち方は記録済みデータの構造そのものであり、**後から遡って入れ直すことができない**。したがって
突合を実装するより前に決めておく必要がある。

### 単調時計には性質の異なる2種類がある

macOSの単調時計は2系統あり、スリープ中の扱いが異なる。

| 系統 | Swift | C | スリープ中 |
|---|---|---|---|
| 連続 | `ContinuousClock` | `mach_continuous_time()` | **進む** |
| 中断 | `SuspendingClock` | `mach_absolute_time()` | 止まる |

単に「単調時計」とだけ決めるとここが未定のまま実装に渡り、選択次第で記録の意味が変わる。

中断側を選ぶと、スリープした分だけタイムラインが詰まる。音声のキャプチャはスリープ中どのみち
止まるので記録の欠落自体は同じだが、**欠落区間の長さが実際の経過時間と一致しなくなる**。
その結果、実時刻アンカーからの換算がスリープをまたいだ時点でずれ、突合の基盤が崩れる。

### 単一のアンカーでは足りない

セッション開始時点の実時刻を1回だけ記録する方式には2つの弱点がある。

- セッション全体の実時刻への対応が、開始時の1サンプルに依存する。その瞬間にNTPがずれていれば、
  セッション全体がまとめてずれる。
- 長時間のセッションでは、その間に生じるクロックのドリフトやNTP補正を後から検出できない。

### 時刻精度は突合にとって硬い要件ではない

突合において、2台のwall clockが完全に一致している必要は実はない。自分が話した瞬間、相手側では
それがほぼ同時に鳴る(ネットワーク遅延は数十ms程度)。つまり**両者の記録には共通の信号が含まれている**。

したがって時刻がずれていても、双方のレベル時系列を相互相関にかければオフセットを実測で求められる。
アンカーはその初期推定値として働けばよく、NTPの精度を事前に証明する必要はない。

### 先行研究における位置づけ

上記の構造は、センサネットワークの時刻同期研究における **Reference Broadcast Synchronization**
(Elson, Girod, Estrin, OSDI 2002) の2つの中核アイデアと一致する。

- **受信者同士の同期(receiver-receiver synchronization)** — 送信側と受信側を同期させるのではなく、
  両者が共通に観測した参照信号を使って受信者同士を合わせる。送信経路の非決定性を回避できる。
  我々の場合、この参照ブロードキャストにあたるのが音声そのものである。
- **事後同期(post-facto synchronization)** — クロックは普段自由に走らせておき、必要になった時点で
  遡って合わせる。[ADR-0006](0006-file-exchange-before-p2p.md)で常時通信しないと決めたことと整合する。

一方、時刻の表現については **TrueTime**(Spanner, OSDI 2012)の考え方を採る。TrueTimeは時刻を
単一の値ではなく `[earliest, latest]` の区間として返し、**不確かさを隠さずAPIに出す**。
GPSや原子時計は当然使えないが、この表現の形は我々にも有効である。実時刻への換算値を正確なものとして
扱ってしまうと、分析時に根拠のない精度で events を比較することになる。

## 決定

- 各レコードは、**セッション開始からの連続単調時刻**(`ContinuousClock` / `mach_continuous_time()`)
  のオフセットを持つ。スリープ中も進む側を使う。
- **実時刻アンカーを定期的に記録する。** アンカーは「その時点の実時刻(UTC)」と「対応する連続単調時刻」
  の組。セッション開始時に1つ、以降は一定間隔(数分程度)で追加する。
- 実時刻が必要な場面では、対象時刻を挟む2つのアンカーから換算する。
- **実時刻への換算値は点ではなく、不確かさを伴う区間として扱う。** 換算に使ったアンカー間隔と、
  その区間で観測されたドリフト量から不確かさの幅を導く。単調オフセット自体は機械内で正確なので、
  不確かさが生じるのは実時刻へ換算する場面と、2台の記録を突き合わせる場面に限られる。
- 表現は、単調オフセットをマイクロ秒のInt64、実時刻をUTCエポックのマイクロ秒とする。
  タイムゾーンとDSTは保存時点では扱わない(表示時にローカルへ変換する)。

## 影響

- スリープやNTP補正があっても、セッション内の区間長と順序は壊れない。スリープをまたいでも
  記録の欠落区間の長さが実際の経過時間と一致する。
- アンカーが複数あるため、**事後にクロックのドリフトを検出・補正できる。** アンカー間で
  実時刻の進みと単調時刻の進みを比較すれば、そのずれがそのままドリフト量になる。
- 2台の記録の突合は、まずアンカー経由で大まかに合わせ、必要ならレベル時系列の相互相関で
  精密化する、という2段構えが取れる。**時刻精度の検証を突合の着手前に済ませておく必要がない。**
- 保存量への影響はほぼない。レコードごとに増えるのは8バイトのオフセットのみで、アンカーは
  数分に1行にすぎない。
- アンカーの記録間隔という運用パラメータが1つ増える。短くすればドリフト追跡の解像度が上がるが、
  数分間隔で十分と考えられる(想定するドリフトの大きさに対して、突合が要求する精度は桁で緩い)。
- 実時刻を区間で扱うため、分析側は「この2つの事象は±Xms以内に起きた」という形でしか答えられなくなる。
  これは制約ではなく正確さであり、**根拠のない精度で events を並べてしまう事故を防ぐ。**
  要望書の目的は劣化の切り分けであって、ミリ秒単位の厳密な順序づけではないため実用上の支障はない。

## 検討した代替案

### Huygens (NSDI 2018) 等の高精度クロック同期

coded probeとSVMによるフィルタリング、および「対同期したクロック群は推移的に同期する」という
ネットワーク効果を利用して数十ナノ秒の精度を達成する手法。**採用しない。**

常時のプローブ交換と多数ノードの存在が前提であり、[ADR-0006](0006-file-exchange-before-p2p.md)で
決めた「セッション中は通信しない・2台のみ」という構成と噛み合わない。加えて、我々が必要とする精度は
この水準から6〜7桁緩い(20msフレームが最小粒度)。

### 論理クロック(Lamport clock / vector clock / Hybrid Logical Clocks)

**採用しない。扱っている問題が異なる。**

これらが捉えるのは事象間の因果関係の順序であり、物理時刻の対応づけではない。我々の2エージェントは
セッション中に一切メッセージを交換しないため、順序づけるべき因果関係がそもそも存在しない。
必要なのは「同じ物理時刻に何が起きていたか」の対応づけである。

HLC (Kulkarni, Demirbas et al.) は物理時刻と因果性を両立させる優れた手法だが、それが解くのは
一貫スナップショットの取得やトランザクション順序といった別の問題であり、本件には適用されない。
「分散システムの時刻」で最初に想起される手法であるため、意図的に採用しないことをここに記録しておく。

# ADR-0007: 配布用バイナリはCIで署名済みとして作り、タグで公開する

## ステータス

Accepted (2026-09-12)

## 背景

実装が一通り揃い、実機で動かす段になった。ここで決めるべきは**どうやってバイナリを手元と
相手側のMacに届けるか**である。

一見すると単なるビルドの自動化だが、このアプリに限っては**署名の同一性が本題**になる。

### ad-hoc署名のままでは継続的デプロイが成立しない

[スパイク](../experiments/macos-app-bundle-spike-result.md)で実機確認済みのとおり、ad-hoc署名では
コードを1行変えるだけでCDHashが変わり、TCCから見て**まったく別の未知のアプリ**になる。許可は
維持されず、マイクの許可ダイアログが再び出る。

CDは、その性質上コードが変わるたびにバイナリを作る。ad-hoc署名のまま配れば、**更新のたびに
利用者がマイクの許可をやり直すことになる。** 常駐して勝手に記録し続けることが要件の前提なのに、
更新のたびに手を止めさせるのでは、自動で配る意味がない。

つまりCDを入れるなら、安定した署名の同一性を持つ証明書がCI側に要る。これは「あったほうがよい」
ではなく、**CDを名乗るための必要条件**である。

### 相手側にビルドを要求できない

[ADR-0006](0006-file-exchange-before-p2p.md)で相手側もmacOSとしたが、それは動かす環境の話であって、
Swiftツールチェインを入れてもらう話ではない。突合のために相手に記録してもらう以上、
渡すのは**開いて起動できるもの**でなければならない。

## 決定

**CIで署名済みの `.app` を作り、タグを打ったらReleaseとして公開する。**

- 署名の identity は秘密情報として持たせ、ワークフローが一時キーチェーンに取り込んで使う。
  identity が無い場合は ad-hoc にフォールバックし、**許可を失う旨を出力に明示する。**
  黙ってad-hocで配るのが、いちばんまずい。
- Developer ID と notarization の資格情報が揃っていれば、公証まで通してステープルする。
  無ければ自己署名のまま公開し、初回だけ隔離属性を外す手順を添える。
- 成果物は **universal binary** にする。ランナーは arm64 だが、相手側のMacがIntelである可能性を
  こちらから排除できない。ビルド時間が倍になるだけで、届かない可能性を消せる。
- `main` への push では成果物をアーティファクトとして残すだけにし、公開はタグに限る。
  常駐アプリを勝手に更新し続けると、いつの版が動いているのか利用者が分からなくなる。

## 採用しなかった選択肢

- **ad-hoc署名のまま配る。** 上記のとおり更新のたびに許可を失う。手でビルドしていた頃は
  「開発中だから」で済んだが、配る段では通らない。
- **相手側にビルドしてもらう。** ツールチェインの導入を要求することになる。動かす環境と
  作る環境は別で、後者まで求める理由がない。
- **App Store 配布。** サンドボックスが必須になり、記録の保存先に制約が増える。個人と
  その相手のためのツールに審査の周期を持ち込む理由がない。
- **Homebrew tap。** 配布経路としては妥当だが、まず署名済みの成果物が要る。順序の問題で、
  排除ではない。

## 未検証の前提

以下は**まだ確かめていない。** いずれも実機でしか決着しない。

- **自己署名証明書で許可が維持されるか。** スパイクが示したのはad-hoc署名での挙動まで。
  安定した identity なら維持される見込みだが、実挙動は未検証。
- **hardened runtime でマイクが取れるか。** 公証には hardened runtime が要り、その下では
  `com.apple.security.device.audio-input` の entitlement が無いとマイクを取れない。付与はするが、
  実際に取れるかは未確認。
- **公証が通るか。** 資格情報を持っていないため、ワークフローの分岐ごと未実行。

決着のさせ方は決まっている。**同じ証明書で2回リリースを流し、その間にコードを変え、
2回目の起動で許可ダイアログが出ないことを見ればよい。** ad-hocとの差がそこに出る。

# ADR-0015: 記録の時刻はフレーム数で刻み、途切れたときだけ連続単調時計で継ぎ直す

## ステータス

Proposed (2026-09-13)

## 背景

[ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md) は Accepted だが、**実装されていない。**

```swift
// RecordingPipeline.swift:98-101
// 時刻はフレーム番号から決める。処理時刻を読むと、1バッファぶんのフレームが
// ほぼ同じ時刻になってしまい、レベルの時系列として使えない。
let monotonicUs = frameIndex * configuration.frameDurationUs
frameIndex += 1
```

`ContinuousMonotonicClock` は `Clock.swift` に書かれているが、製品コードのどこからも作られていない。
記録に入っている `monotonic_us` は、連続単調時計の読みではなく、**そのストリームが受け取った
フレームの通し番号に 20ms を掛けた値**である。

### フレーム番号を使った理由は正しい

AVAudioEngine は約100msのバッファでまとめて渡してくる(`AudioCapture.swift:122` の実測メモ)。
1バッファは5フレームになる。ここで各フレームに処理時刻を入れると、5フレームが同じ時刻を持つ。
20ms刻みのレベル時系列として使えなくなる。上のコメントが言っているのはこのことで、これは正しい。

問題は、フレーム番号が**音が流れている間しか進まない**ことにある。ADR-0003 は中断単調時計
(`mach_absolute_time()`)を「スリープした分だけタイムラインが詰まる」という理由で退けたが、
フレーム番号はそれより極端である。中断時計が止まるのはスリープ中だけで、フレーム番号は
キャプチャが止まっている間ずっと止まる。

### いま何が壊れているか

1. **欠落区間が記録から消える。** デバイスの差し替え(#12)やタップの張り直し(#13)で
   取りこぼした20分は、記録の上では0秒になる。記録が「その間ずっと静かだった」と読める形になり、
   [ADR-0008](0008-process-tap-for-received-audio.md) が避けようとした「記録上は正常」を作る。

2. **アンカーが壊れる。** `AnchorScheduler` は5分ごとにアンカーを打つが、単調側は「音が流れた5分」、
   実時刻側は本当の経過時間である。欠落があればアンカー間の傾きが 1 から外れ、
   `ClockConversion.interpolate` はその差をまるごとドリフト量として読む。
   100ppm(5分で30ms)を想定して置いた不確かさの幅に、桁の違う値が入る。
   不確かさを正直に出すための仕組みが、いちばん大きな嘘をつく場所になる。

3. **2本のストリームが別のタイムラインに乗る。** マイクと出力タップはそれぞれ自分の `frameIndex` を
   持ち、どちらも 0 から始まる。出力タップは誰も音を鳴らしていなければフレームを受け取らないので、
   両者の 0 は同じ瞬間ではないし、以降も同じ速さでは進まない。
   [ADR-0012](0012-multiparty-meetings.md) の突合は、まず同じ機械の中で2本が並ぶことを前提にしている。
   それが成り立っていない。

4. **`clock_anchors` が上書きされる。** 主キーは `(session_id, monotonic_us)` で、書き込みは
   `INSERT OR REPLACE` である。2本のストリームがどちらも 0 近傍から始まるため、
   セッション開始直後のアンカーは衝突し、後から書いた方が前を消す。

5. **[ADR-0014](0014-suspend-when-not-speaking.md) の10分が10分にならない。** 休止判定は
   `monotonicUs` の差で無発話の長さを測る。フレーム番号のままでは、これは「音が流れた10分」であって、
   ADR-0014 が書いた10分ではない。

(1) と (2) と (5) は時刻の刻み方の問題、(3) と (4) は時計を共有していないことの問題である。

## 決定

### 1. フレーム数で自由に走らせ、ずれたときだけ継ぎ直す

パイプラインは連続単調時計を1つ持つ。バッファを受け取るたびに、そのバッファの先頭フレームが
持つはずの時刻(フレーム数から決まる値)と、時計の読みを比べる。差が閾値を超えたときだけ、
時計の読みへ乗り換える。

```
monotonicUs = baseUs + frameIndex * frameDurationUs
```

継ぎ直しは `baseUs` を時計の読みに差し替え、`frameIndex` を 0 に戻すことで行う。

キャプチャが続いている間は、時刻はフレーム数だけで決まる。バッファの到着ジッタは入らず、
20ms刻みは正確に20ms刻みのままになる。キャプチャが途切れた区間は、実際の経過時間ぶん空く。
どちらも、いま欲しい性質そのものである。

閾値は **500ms** とする。1バッファ(約100ms)の到着遅れと、その揺れを吸収し、
かつ「取りこぼし」と呼ぶべき長さより十分に短い。

### 2. 最初のバッファでも継ぎ直す

`baseUs` の初期値は持たず、最初のバッファで時計から決める。セッション開始から
キャプチャが実際に始まるまでの時間(エンジンの起動、タップの確立、許可の応答)は
ストリームごとに違う。2本のストリームの原点が違うのは事実であり、それを 0 に揃えると、
実際にはずれている2本を「同時に始まった」と記録することになる。

### 3. 継ぎ直しは前へだけ

`seconds` の主キーは `(stream_id, monotonic_us)` である。時刻を戻すと、既存の行を黙って上書きする。
時計の読みがフレーム数から決まる時刻より**手前**だった場合は継ぎ直さない。
前方へのジャンプだけを許す。

これは取りこぼしの検出に非対称性を持ち込むが、非対称なのは問題の方である。
時刻が前に飛ぶのは「記録できなかった区間があった」ことを意味し、後ろに戻るのは
「時計の読みかフレーム数のどちらかが少しずれた」ことしか意味しない。

### 4. 時計はセッションにひとつ

`ContinuousMonotonicClock` はセッション開始時に1つ作り、マイクと出力タップの両方のパイプラインに
同じインスタンスを渡す。`startTicks` が共有されるので、2本のストリームは同じ原点を持つ。

これで (3) が直る。(4) も直る — 時計を共有すれば、2本の最初のアンカーは違う `monotonic_us` を持つ。
共有した上でなお同じ値になった場合、それは2本が同じ対応点を記録したということであり、
`INSERT OR REPLACE` が片方を消しても失うものはない。

### 5. 継ぎ直した時点でアンカーを打つ

継ぎ直しは、キャプチャが止まっていた区間をまたいだことを意味する。その前後は換算の連続性が
保証されない。継ぎ直した時点でアンカーを1本打てば、欠落区間がアンカーで挟まれ、
外挿ではなく内挿で換算できるようになる。

## 影響

- **記録済みのデータは違うタイムラインに乗っている。** ADR-0003 が「後から遡って入れ直すことが
  できない」と書いたとおりで、入れ直す手段はない。開発中に溜めたものなので捨てる。
- 分析側は、記録の空隙を「静かだった」と「測れていなかった」に区別できる必要が出てくる。
  いまの表示はこれを持っていない。#7 の表示側で扱う。
- `RecordingPipeline` の初期化に時計が1つ増える。テストでは固定の時計を差し替えて、
  継ぎ直しの条件を直接組める(`MonotonicClock` がプロトコルなのはこのためである)。
- 音のスレッドで時計を読むことになる。`mach_continuous_time()` は確保もロックも伴わないので、
  #10(IOスレッドでの確保をなくす)を悪化させない。
- 閾値という運用パラメータが1つ増える。短すぎればバッファの遅れで継ぎ直しが頻発して
  タイムラインが荒れ、長すぎれば短い取りこぼしを吸収して見えなくする。

## 検討した代替案

### フレームごとに時計を読む

**採用しない。** 1バッファぶんのフレームがほぼ同じ時刻を持ち、レベルの時系列として使えなくなる。
`RecordingPipeline` のコメントが書いているとおりである。

### バッファの先頭で時計を読み、フレーム番号でオフセットする

毎バッファ時計に乗り換える方式。**採用しない。**

バッファ到着のジッタがそのままタイムラインに入り、時刻が前後する。
`PRIMARY KEY (stream_id, monotonic_us)` の下では、戻った時刻が前の行を黙って上書きする。
書いたはずの1秒が消え、しかもエラーは出ない。挙げた案の中でいちばん危ない。

### ホストタイムを使う

いちばん正確な選択肢であり、**いまは採らないが、後から移れる。**

AVAudioEngine のタップ閉包は `AVAudioTime` を受け取り、Core Audio の IO ブロックは
`AudioTimeStamp` を受け取る。どちらもそのバッファが実際にキャプチャされたホストタイムを持っている。
いまのコードはこれを捨てている(`AudioCapture.swift:125` の `{ buffer, _ in }`、
`SystemOutputTap` の `handle` は `AudioTimeStamp` を引数に取っていない)。
これを使えば、到着の遅れも欠落の長さも、推定ではなく実測になる。

採らない理由は2つある。ホストタイムは `mach_absolute_time` の基数にあり、ADR-0003 が退けた
「スリープ中に止まる」側である。連続側へ移すには、バッファ到着時に両方の時計を読んで差を取る
必要があり、その差はスリープをまたぐたびに変わる。もう1つは、デバイスのクロックとホストの
クロックの間のドリフトを別に扱うことになる点で、いずれも実機でしか確かめられない。

重要なのは、**保存する表現はどちらでも同じ**だということである。セッション開始を原点とする
連続単調時計のマイクロ秒オフセット、という ADR-0003 の表現は変わらない。変わるのは
その値をどこから得るかだけで、これは記録済みデータを壊さずに後から差し替えられる。
ADR-0003 が「後から入れ直せない」と言ったのは表現のことであって、精度の出どころのことではない。

### ADR-0003 を書き換えて、フレーム番号を正式な時刻とする

**採用しない。** 上に挙げた5つの壊れ方は、どれも記録の意味そのものに関わる。
とくに「取りこぼした区間が記録から消える」は、この道具が答えようとしている問い
——「あのとき聞こえにくかったのは何が起きていたからか」——に対して、
いちばん質の悪い答え方をする。何も起きていなかったことにする。

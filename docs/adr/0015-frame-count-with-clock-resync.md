# ADR-0015: 記録の時刻はフレーム数で刻み、途切れたと分かったときだけ基準を打ち直す

## ステータス

Proposed (2026-09-13)

## 背景

[ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md) は Accepted だが、**実装されていない。**

```swift
// RecordingPipeline.swift:98-101
// 時刻はフレーム番号から決める。処理時刻を読むと、1バッファぶんのフレームが
// ほぼ同じ時刻になってしまい、レベルの時系列として使えない。
let monotonicUs = frameIndex * configuration.frameDurationUs
frameIndex += 1
```

`ContinuousMonotonicClock` は `Clock.swift` に書かれているが、製品コードのどこからも作られていない
(生成しているのは `ClockTests.swift` だけである)。記録に入っている `monotonic_us` は、
連続単調時計の読みではなく、**そのストリームが受け取ったフレームの通し番号に 20ms を掛けた値**である。

### フレーム番号を使った理由は正しい

AVAudioEngine は約100msのバッファでまとめて渡してくる(`AudioCapture.swift:122` の実測メモ)。
1バッファは5フレームになる。ここで各フレームに処理時刻を入れると、5フレームが同じ時刻を持つ。
20ms刻みのレベル時系列として使えなくなる。上のコメントが言っているのはこのことで、これは正しい。

問題は、フレーム番号が**音が流れている間しか進まない**ことにある。ADR-0003 は中断単調時計
(`mach_absolute_time()`)を「スリープした分だけタイムラインが詰まる」という理由で退けたが、
フレーム番号はそれより極端である。中断時計が止まるのはスリープ中だけで、フレーム番号は
キャプチャが止まっている間ずっと止まる。

### いま何が壊れているか

1. **欠落区間が記録から消える。** デバイスの差し替えやタップの張り直しで取りこぼした20分は、
   記録の上では0秒になる。記録が「その間ずっと静かだった」と読める形になり、
   [ADR-0008](0008-process-tap-for-received-audio.md) が避けようとした「記録上は正常」を作る。

2. **アンカーからの換算が壊れる。** `AnchorScheduler` は5分ごとにアンカーを打つが、単調側は
   「音が流れた5分」、実時刻側は本当の経過時間である。取りこぼしがあれば、アンカー間で
   実時刻の進みだけが大きくなる。

   内挿の枝(`Clock.swift:130-144`)は、その差をまるごと不確かさとして返す。20分取りこぼせば、
   その区間の換算は ±20分の幅を持つ。嘘ではないが、使えない。

   外挿の枝(`Clock.swift:104-109`)はもっと悪い。単調時刻の差をそのまま実時刻の差として足し、
   不確かさは `assumedDriftPpm` の 100ppm ぶん——5分で30ms——しか見込まない。
   **取りこぼしの分だけずれた実時刻が、±30ms の精度を名乗って返る。**

3. **2本のストリームが別のタイムラインに乗る。** マイクと出力タップはそれぞれ自分の `frameIndex` を
   持ち、どちらも 0 から始まる。出力タップは誰も音を鳴らしていなければフレームを受け取らないので、
   両者の 0 は同じ瞬間ではないし、以降も同じ速さでは進まない。
   [ADR-0012](0012-multiparty-meetings.md) の突合は、まず同じ機械の中で2本が並ぶことを前提にしている。

4. **`clock_anchors` が上書きされる。** 主キーは `(session_id, monotonic_us)` で、書き込みは
   `INSERT OR REPLACE` である。2本のストリームがどちらも 0 近傍から始まるため、
   セッション開始直後のアンカーは衝突し、後から書いた方が前を消す。

5. **[ADR-0014](0014-suspend-when-not-speaking.md) の10分が10分にならない。** 休止判定は
   `monotonicUs` の差で無発話の長さを測る。フレーム番号のままでは、これは「音が流れた10分」であって、
   ADR-0014 が書いた10分ではない。

## 決定

### 1. 時刻はフレーム数で刻み、基準点を持つ

```
monotonicUs = baseUs + frameIndex * frameDurationUs
```

キャプチャが続いている間、時刻はフレーム数だけで決まる。バッファの到着ジッタは入らず、
20ms刻みは正確に20ms刻みのままになる。これはいまの挙動と同じで、変えない。

### 2. 基準を打ち直すのは、途切れたと**分かっている**ときだけ

`baseUs` を連続単調時計の読みに差し替え、`frameIndex` を 0 に戻す。これを行うのは次の場合に限る。

- 最初のバッファ(エンジンまたはタップの開始)
- 停止してからの再開(ADR-0014 の休止・再開、タップの張り直し)
- `AVAudioEngineConfigurationChange` — デバイスの差し替え
- 音声層が報告するサンプル時刻の不連続(**未検証。下記「確かめること」を参照**)

**時計とのずれが閾値を超えたら打ち直す、という形は採らない。** 理由は後述する。

### 3. ドリフトは打ち直さない。アンカーに測らせる

デバイスのクロックは公称レートちょうどでは動かない。フレーム数から作った時刻は、
実際の経過時間に対してじわじわずれていく。これを打ち直しで吸収してはならない。

**このずれを測るのがアンカーの仕事だからである。** アンカーを時間をおいて2つ打てば、
実時刻の進みと単調時刻の進みの差がそのまま出る。`ClockConversion.interpolate` は
それを不確かさとして返す(`Clock.swift:142`)。ADR-0003 が「事後にクロックのドリフトを
検出・補正できる」と書いたのはこの仕組みのことである。

打ち直しで吸収すると、ドリフトはタイムラインの中に呑まれて、アンカーからは見えなくなる。
**測るために置いた仕組みの目の前で、測るべきものを消すことになる。**

### 4. 打ち直すときは、途中の状態を捨てる

打ち直しの時点で、次が中途半端に残っている。

- `Framer` の端数サンプル(最大 `frameLength - 1`、48kHz・20msなら959サンプル)
- `Aggregator` の溜まりかけの1秒(最大49フレーム)
- `SpeechDetector` の30秒窓

捨てないと、**欠落の前と後のフレームが1つの秒に混ざる。** 欠落前の30フレームと欠落後の20フレームで
1行が完成し、`monotonic_us` は欠落前を指し、`frame_count` は 50 になる。主キーは衝突せず、
1秒に満たない行にもならない。**完全に見える嘘の行**であり、あとから検出する手がかりが何も残らない。
衝突してくれたほうがまだよかった。

したがって、打ち直しの前に `Aggregator.flush()` で端数の秒を書き出し(`frame_count` が
50未満になるので、短い秒だと分かる)、`Framer.reset()` で端数サンプルを捨て、
`SpeechDetector` の窓もリセットする。

窓のリセットが要るのは、雑音フロアが**その環境のもの**だからである。デバイスを差し替えたあとに
差し替え前のフロアが30秒間効くと、静かな機器へ移った場合は発話を拾えず(ADR-0014 の
カウンタに嘘の無発話が積まれる)、うるさい機器へ移った場合は `lowLevel` が再開直後に誤って立つ。

### 5. アンカーはストリーム単位で持つ

`clock_anchors` に `stream_id` を足し、主キーを `(stream_id, monotonic_us)` にする。

いまセッション単位になっているのは、「同じ機械の同じ時計で観測されるのだから二重に持つ必要がない」
という理由による(`RecordingStore.swift` の記述)。**フレーム数で刻む以上、これは成り立たない。**
2本のストリームは別のデバイスのクロックに乗っており、公称レートからのずれ方が違う。
片方のアンカーでもう片方の時刻を換算すれば、その差だけ間違う。

ストリームごとに持てば、主キーが分かれるので (4) の上書きも同時に消える。

### 6. 時計はセッションにひとつ

`ContinuousMonotonicClock` はセッション開始時に1つ作り、両方のパイプラインに同じインスタンスを渡す。
`let` だけを持つので共有して安全だが、`Sendable` を明示する。

これで2本のストリームの原点が揃い、`monotonic_us` を素で並べておおよそ比較できるようになる。
**おおよそ**である。正確に並べるには (5) のストリームごとのアンカーを経由する。

### 7. 空隙は理由つきで記録する

打ち直しのたびに、欠落の区間(直前のフレームの時刻と、新しい `baseUs`)と理由を残す。
記録の空隙が「静かだった」のか「測れていなかった」のかは、これでしか区別できない。

理由まで残せるのは、(2) で打ち直しを既知の事象に限ったからである。
閾値で推測する形では「なぜか合わなかった」としか書けない。

## 確かめること

**未知の取りこぼしを拾う手段が、(2) の4つ目にしかない。** エンジンが走ったまま、
過負荷やタップの不調でバッファが飛んだ場合、こちらの知っている事象は何も起きない。

音声層はこれを報告できるはずである。AVAudioEngine のタップ閉包は `AVAudioTime` を、
Core Audio の IOブロックは `AudioTimeStamp` を受け取り、どちらもデバイスのサンプル時刻を持つ。
サンプル時刻がバッファ長ぶんより大きく飛んでいれば、その間のサンプルは落ちている。
いまのコードはこれを捨てている(`AudioCapture.swift:125` の `{ buffer, _ in }`、
`SystemOutputTap` の `handle` は `AudioTimeStamp` を引数に取っていない)。

**この環境には Swift ツールチェインも音声デバイスも無いので、確かめられない。**
実機スパイクで次を確かめてから実装する。

- 両経路でサンプル時刻が取れるか。取れるとして、連続しているか
- バッファを意図的に落としたとき、サンプル時刻の飛びとして現れるか
- 2本のストリームのサンプル時刻が同じ基数に乗っているか

取れないと分かった場合は、未知の取りこぼしは検出できないものとして扱い、
ADR を書き換える。閾値方式へ戻すのではない——下記のとおり、閾値は取りこぼしを検出できない。

## 影響

- **記録済みのデータは違うタイムラインに乗っている。** ADR-0003 が「後から遡って入れ直すことが
  できない」と書いたとおりで、入れ直す手段はない。開発中に溜めたものなので捨てる。
- `clock_anchors` に `stream_id` が増える。既存の行は捨てるので移行は要らない。
- 空隙を残す表が1つ増える。
- 分析側は、記録の空隙を「静かだった」と「測れていなかった」に区別できる必要が出てくる。
  いまの表示はこれを持っていない。2本目のストリームを表示へ通す作業と一緒に扱う。
- アンカーは「フレームの捕捉時刻」と「バッファ到着時の実時刻」を組にする。1バッファぶん
  (約100ms)の未知のずれを含む。ADR-0003 が「時刻精度は突合にとって硬い要件ではない」
  「アンカーは初期推定値として働けばよい」と書いた範囲に収まるが、不確かさの幅には現れないので
  ここに書いておく。
- 音のスレッドで時計を読むことになる。`mach_continuous_time()` が確保もロックも伴わないことは、
  この場では確かめられていない。[ADR-0016](0016-handoff-off-the-audio-thread.md) の実装と合わせて、
  実機で確かめる。ADR-0016 は時刻を音のスレッドで採ってリングに載せると決めているので、
  この読みはそちらの「ロックを取らない」制約の下に入る。

## 検討した代替案

### 時計とのずれが閾値を超えたら打ち直す

この ADR の最初の案がこれだった(500ms)。**採用しない。閾値は取りこぼしを測れない。**

フレーム数から作った時刻は、公称レートと実クロックのずれ ε ppm ぶん、実時間に対して
毎秒 ε マイクロ秒ずれる。閾値 500ms に達するまでの時間は `0.5 / (ε × 10⁻⁶)` 秒である。

| ずれ | 500ms に達するまで |
|---|---|
| 100ppm(ADR-0003 が想定した値) | 5000秒 = 1時間23分 |
| 500ppm(Bluetooth 級) | 1000秒 = 16分40秒 |

**取りこぼしが1つも無くても、会議中に打ち直しが起きる。** しかも記録の上では、本物の欠落と
区別がつかない。ADR-0003 が「事後に検出・補正できる」ようにしたドリフトが、
空隙として記録されることになる。

逆向きも壊れている。打ち直しを前方へだけに限ると(`seconds` の主キーが
`(stream_id, monotonic_us)` なので、時刻を戻せば既存の行を黙って上書きする)、
実クロックが公称より**速い**機械では打ち直しが起きない。+100ppm で8時間走れば、
フレーム時刻は実時間より 2.88秒 先行する。この先行ぶん `D` はそのまま実効閾値に足されるので、
**8時間目には 3.4秒未満の取りこぼしが黙って呑まれる。** `D` はどこにも記録されない。

閾値方式は、測れるもの(ドリフト)を空隙として記録し、測りたいもの(取りこぼし)を
時間とともに見逃す。向きが逆である。

### フレームごとに時計を読む

**採用しない。** 1バッファぶんのフレームがほぼ同じ時刻を持ち、レベルの時系列として使えなくなる。
`RecordingPipeline` のコメントが書いているとおりである。

### バッファの先頭で時計を読み、フレーム番号でオフセットする

毎バッファ時計に乗り換える方式。**採用しない。**

バッファ到着のジッタがそのままタイムラインに入り、時刻が前後する。
`PRIMARY KEY (stream_id, monotonic_us)` の下では、戻った時刻が前の行を黙って上書きする。
書いたはずの1秒が消え、しかもエラーは出ない。

### ホストタイムをそのまま記録の時刻にする

バッファが実際にキャプチャされたホストタイムを、そのまま `monotonic_us` にする。**採用しない。**

ホストタイムは `mach_absolute_time` の基数にあり、ADR-0003 が退けた「スリープ中に止まる」側である。
連続側へ移すには、バッファ到着時に両方の時計を読んで差を取ることになり、その差は
スリープをまたぐたびに変わる。加えて、デバイスのクロックとホストのクロックの間のドリフトを
別に扱うことになる。

ただしサンプル時刻は上の「確かめること」のとおり**取りこぼしの検出に使う。**
時刻そのものにはしないが、捨てもしない。

### ADR-0003 を書き換えて、フレーム番号を正式な時刻とする

**採用しない。** 上に挙げた5つの壊れ方は、どれも記録の意味そのものに関わる。
とくに「取りこぼした区間が記録から消える」は、この道具が答えようとしている問い
——「あのとき聞こえにくかったのは何が起きていたからか」——に対して、
いちばん質の悪い答え方をする。何も起きていなかったことにする。

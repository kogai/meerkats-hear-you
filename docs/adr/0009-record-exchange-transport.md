# ADR-0009: 記録の交換経路をどうするか

## ステータス

Proposed (2026-09-12)

## 背景

突合の形が定まった。**同じエージェントが発話(マイク)と聞こえ(受信音声)の両方を記録し、
交換器が記録をやり取りして、自分の発話と相手の聞こえを突き合わせる。**

[ADR-0006](0006-file-exchange-before-p2p.md)は荷物と経路の2つを決めていた。このうち荷物
(JSON、範囲限定、利用者が読める)はプライバシー要件から来ているのでそのまま生きる。
**論点は経路だけである。**

### 送るのは聞こえだけでよい

突合の向きから、ひとつ強い性質が出る。自分の発話と相手の聞こえを突き合わせるなら、必要なのは
**相手の聞こえ**であって、自分のマイク記録ではない。

つまり**自分のマイク記録は一切外に出ない。** 相手へ渡すのは自分の聞こえ、すなわち
**相手自身の声から作ったレベル記録**である。自分の声の記録は手元に残る。実装を信用しなくても
成立する構造上の性質で、経路をどれに決めても変わらない。

ただし多人数の会議では、自分の聞こえに第三者の声も混ざる。その場合この性質は崩れる。

### 経路が届かない

[ADR-0006](0006-file-exchange-before-p2p.md)はP2Pの手段としてBonjourを挙げていたが、これは
同一LAN内しか届かない。**オンライン会議の相手は通常べつのネットワークにいる。** 要件の中心で
ある遠隔の相手と、まさに繋がらない。

NATを越えるには中継が要るが、中継は要望書の「そもそもクラウドにデータを送らない」に触れる。

### 「暗黙に送らない」の担保が構造から運用に落ちる

ADR-0006のファイル交換は、アプリが自発的に通信する経路そのものを持たないことで、この要件を
**構造的に**満たしていた。通信経路を持った時点でこの保証は失われ、同意フローで埋めるほかなくなる。

## 選択肢

| | 届く範囲 | 前提ツール | 運用 |
|---|---|---|---|
| A. LAN内はP2P、外はファイル | LAN内は自動、外は手作業 | なし | なし |
| B. NAT越えP2P (STUN、中継なし) | 回線次第 | なし | 外部STUNへの依存 |
| C. オーバーレイ前提 (Tailscale等) | どこでも | **相手にも導入を要求** | なし |
| D. 中継サーバ | どこでも | なし | **自分が持つ** |

Dは経路の問題が丸ごと消えるが、要望書の「そもそもクラウドにデータを送らない」に正面から触れる。
採るなら端から端まで暗号化し、中継は暗号文を預かる箱に徹する形になる。下記の方向により採らない。

送る中身の下限(内容が復元できない水準をどう担保するか)は経路とは独立なので、
[ADR-0010](0010-recording-floor-broadband-only.md)に分けた。記録する側にも同じ基準がかかるためである。

## 方向: Bを本線とする

**解くべきはリモートワークの会議であり、相手は常にべつのネットワークにいる。** Aの自動経路
(LAN内)はその場面でまず使えない。したがってBを本線に置き、Dの中継は採らない。

ただしBには、名前から受ける印象と実際の姿に差がある。以下2点はBを選ぶなら避けて通れない。

### 既存研究が示す成功率

穴あけ(hole punching)は[Fordら(USENIX ATC 2005)](https://pdos.csail.mit.edu/papers/p2pnat.pdf)が
体系化した技法で、当時の計測でUDPが約82%、TCPが約64%のNATで成功するとされた。

より最近では、IPFSの本番網で使われているDCUtR(Direct Connection Upgrade through Relay)を対象に、
**167カ国・85,000以上のネットワークから440万回超の試行**を集めた計測がある
([arXiv:2510.27500](https://arxiv.org/abs/2510.27500) / [arXiv:2604.12484](https://arxiv.org/abs/2604.12484))。

| | 値 |
|---|---|
| 穴あけ段階の成功率 | **70% ± 7.1%** (中継の確保とアドレス取得が成功した条件下) |
| 成功したうちの初回成功 | 97.6% |
| TCPとQUICの差 | 統計的に区別できない |

最後の行は「UDPのほうが通りやすい」という通説を実測で否定している。DCUtRは往復時間に基づく
高精度の同期を行っており、それが効いていると報告されている。

**つまりおよそ3組に1組は直接繋がらない。** 落とし所は必須である。

### シグナリングをどうするか

NAT越えは、互いの公開アドレスをSTUNで知るだけでは成立しない。**知ったアドレスを相手に伝える
経路が別に要る。** そのうえで両側がほぼ同時に送り始めて初めて穴が開く。

**同期の精度は、当初考えたほど厳しくない。** 実測では9割超のケースで遅延の標準偏差が平均往復時間の
半分程度に収まると報告されており、余裕はかなり広い。加えて実装は再送を前提にしていて、
0/250ms/500ms/1s/2sの5回といった schedule が標準である。**両側が繰り返し送っていれば穴は開く。**

マッピングの寿命も制約にならない。[RFC 4787](https://www.rfc-editor.org/rfc/rfc4787.html)はUDPの
マッピングを2分未満で切ってはならない(REQ-5)とし5分以上を推奨している。実際にはこれを守らず
30秒程度で切る実装も報告されているが、STUNのBinding Indicationをkeepaliveとして打てば維持できる。

したがって**サーバを立てない形も成立する。** ランデブーが本当に要るのは、同期のためではなく
**アドレスの更新を配布するため**である。再起動やネットワークの変更でポートが変わったとき、
手渡しの形では相手にそれを伝える手段がない。相手は古い宛先を叩き続けて静かに失敗する。

ランデブーを置く場合、DCUtRの名前(Relay経由で直接接続へ昇格する)が示すとおり、
これは自前の発想ではなく確立した型である。

**預かるだけの掲示板では足りない。** ランデブーが担うのは2つで、互いの送信先(STUNで得た公開
アドレスとローカルアドレス、および公開鍵)の交換と、**穴あけの開始を揃える同期**である。
後者のために両側の往復時間をそこで測る。貼って各自が拾う形では前者しかできない。

これは**中央集権である。** 正確に書くと次のようになる。

| | |
|---|---|
| 止まったとき | 新規の接続ができない。確立済みの接続は生きる。落とし所があるので突合自体は止まらない |
| 見えるもの | 誰と誰がいつ繋いだか、双方のIPアドレス |
| 見えないもの | **記録の中身。経路上に載らない** |

記録が通らない点で**外部STUNに依存するのと同じカテゴリ**であり、Dの中継とは別物。
Tailscaleが直接繋がらないときにDERPで実データを中継するのとも異なり、こちらは中継しない。
ただし**「サーバを持たない」とは言えなくなる。** Bを選ぶことは、暗黙にこれを選ぶことでもある。

### 繋がらない相手が残る

RFC 4787の用語では、NATの振る舞いは Endpoint-Independent Mapping (EIM) と
Endpoint-Dependent Mapping (EDM) に分かれる。同RFCはEIMを要求している(REQ-1)が、EDMは実在し、
そこでは宛先ごとに外側ポートが変わるため穴あけが成立しない。企業網やCGNAT配下で起こりうる。

片側だけがEDMの組は誕生日のパラドックスで救える。計測では**組み合わせの19.6%がこの混在型**で、
両側が256ポートを試すと64%、2048ポート(探索空間の3.1%)まで広げると99.9%で当たる。全体の成功率を
12.5ポイントほど押し上げられる計算になる。**両側がEDMだと0.01%**で、これは中継なしでは諦める領域。

誕生日のパラドックスは後から足せる最適化であり、初期版には要らない。いずれにせよ
**ファイル書き出しを落とし所として必ず残す。** ADR-0006の荷物がそのまま使えるので、追加で決める
ことは無い。

## 端から端までの暗号化は行う

CryptoKitが標準で入っているため依存は増えず、実装量も小さい。

**ただし「暗号化した」だけでは、守りたい相手から守れない。** ランデブーが公開鍵を取り違えて
渡せば、そこで復号できてしまう。経路の暗号化は通りすがりには効くが、**鍵を仲介する当人には
効かない。**

埋めるには鍵の指紋を一度だけ人が突き合わせる必要がある。**ここは安く済む。** 同意フローとして
招待コードの手渡しがどのみち要るので、そこに指紋を載せればよい。二度目以降は保存した鍵と照合し、
変わっていたら警告する(Trust On First Use)。手動の対応づけが既にあるおかげで、ほぼ乗り合わせで済む。

| | |
|---|---|
| 守れる | ランデブーの運用者、経路上の傍受 |
| 守れない | 相手の機械そのもの。復号したあとの記録は相手の手元にある |

残るコストは鍵の寿命である。機械を変えたり入れ直したりすると対が失われ、やり直しになる。
利用者からは「急に繋がらなくなった」として現れるので、**指紋が変わったことを表示で明示する。**

記録がランデブーを通らない以上、暗号化は経路上の保険ではない。**将来もし中継が必要になったとき、
設計を変えずに済ませるための余地**という位置づけになる。

## 決めてほしいこと

**アドレスの更新をどう配る (誰が何を運用するか)。** 上記のとおり同期のためのサーバは要らない。
残る論点はここだけになる。

| | 運用するもの | 代償 |
|---|---|---|
| ア. 手渡し + 常時再試行 | **なし** (公開STUNのみ) | アドレスが古くなったことを相手に伝えられず、静かに失敗する。変わるたびに人が貼り直す |
| イ. 自前のランデブー | 小さなサーバ1つ | 中央集権。止まると新規接続ができない |
| ウ. DHT | **なし** | ブートストラップ先は結局他人のサーバ。公開DHTに存在を告知する。二人で使う道具には重い |
| エ. 既に共有している場所に書く | なし(既存のものに相乗り) | その場所の性質に依存する |

**アが最も軽く、二人で使う道具にはこれで足りる可能性がある。** 対(鍵と身元)は一度決めれば永続する
ので、貼り直すのは短いアドレスだけで、指紋の確認をやり直す必要はない。

イへ移るのは、貼り直しが実際に負担になってからでよい。ADR-0006が手作業を判断点としたのと同じ形で、
**ここでも「実際に困ってから」を判断点にできる。**

## 未検証の前提

- **NAT越えの実挙動。** 作業環境にmacOSが無いため、CIでもコンパイル以上は確かめられない。
- **多人数の会議で自分の聞こえに誰の声が混ざるか。** 上記の性質が崩れる条件を詰めていない。

# ADR-0016: 音のスレッドは値を渡すだけにし、記録は専用のスレッドで書く

## ステータス

Accepted (2026-09-13)

## 背景

いま、SQLiteへの書き込みは音のスレッドから起きている。

```
AudioCapture.handle / SystemOutputTap.handle   ← 音のスレッド
  → RecordingPipeline.ingest
    → sink.write(seconds:)    10秒に1回        ← SQLite
    → sink.write(detail:)     異常に入るたび    ← SQLite (BLOB)
    → sink.write(anchor:)     5分に1回          ← SQLite
```

`Array(UnsafeBufferPointer(...))` による確保と `Date()` も同じ場所にある。

**音のスレッドで時間を使うと音が途切れる。記録しようとしている当の現象を、この道具が自分で作る。**

### 接続の直列化は既にあり、その待ちは短い

接続は `SQLITE_OPEN_FULLMUTEX` で開いてある(`RecordingStore.swift:31`)。
同じ接続を複数のスレッドから呼んでもSQLiteが直列化するので、接続が壊れることはない。

そのうえで訂正しておく。この ADR の最初の版は「分析ウインドウが全行を読む間、接続のミューテックスは
握られたままで、音のスレッドはそこで待つ」と書いていた。**これは誤りである。**
serialized モードのミューテックスはAPI呼び出しごとに取得・解放されるので、音のスレッドが待つのは
読み手の `sqlite3_step` **1回ぶん**にすぎない。28,800行の読み出しの間、書き込みはその合間に入る。
分析ウインドウとの競合は、看板にできるほどのものではなかった。

### 本当に音のスレッドを止めているもの

**(a) WAL の自動チェックポイント。**

`PRAGMA wal_autocheckpoint` を設定していないので、既定の1000ページで働く。
自動チェックポイントは COMMIT の中で走る。つまり**コミットしたスレッド、すなわち音のスレッド**である。
そして `synchronous = NORMAL` でWALのコミットがfsyncを省けるのに対し、
**チェックポイントは本体のDBファイルをfsyncする。**

頻度は実測した([`docs/experiments/wal-growth-result.md`](../experiments/wal-growth-result.md))。
1コミットあたり約2.9ページ積まれ、**1ストリームで57分、2本で26分40秒**で1000ページに達する。
2本で半分より短くなるのは、行が交互に入って触る葉ページが増えるためである。

**会議は1時間前後のことが多い。2本走っていれば、会議1回のあいだに1〜2回は必ず当たる。**
分析ウインドウを開かなくても起きる。

**(b) 詳細層の書き出し。**

なお、チェックポイントの頻度という面では詳細層はほとんど効かない。1分に1回という
最悪に近い頻度でも、到達は1本で57分→49分、2本で26分40秒→23分にしかならない(同上)。
効くのは確保とBLOBの書き込みそのもののほうである。

異常に入るたびに、リングバッファの500フレームを `snapshot()` で配列に写し、
符号化して(500 × 5バイト + ヘッダ)BLOBとして書く。確保と書き込みが両方、音のスレッドで起きる。

`AnomalyDetector` は入りに3秒の継続を求めるが(`sustainedSeconds: 3`)、
**抜けにはヒステリシスが無い。** 1秒でも閾値を割れば `consecutive` も `firing` も落ちる。
同じ種別なら最短4秒に1回、3種別が入れ替われば1〜2秒に1回まで上がりうる。
異常が続いている——つまり利用者が実際に困っている——まさにその間に、いちばん頻繁に起きる。

**(c) 毎バッファの確保。**

`Array(UnsafeBufferPointer(...))` が約100msごとに 48kHz・Float で 19,200バイトを確保する。

頻度の低い重いもの(a)、頻度の高い中くらいのもの(b)、毎回のもの(c)が、全部同じ場所にある。

### `close()` は、片方だけ守られている

`RecordingStore.close()` は `sqlite3_close_v2` のあと `db` を `nil` にする。この `db` は `var` である。

マイク側は `PipelineBox` が `NSLock` の下でパイプラインを切り離すので、`capture.stop()` を過ぎれば
音のスレッドから記録へは届かない。ここは型で守られている。

無防備なのは `SystemOutputTap` である。IOブロックがパイプラインを直接捕まえており、箱が無い。
(`SystemOutputTap.swift` 自身のコメントが「理由があってではなく、まだ手が回っていないため」と書いている。)
[#53](https://github.com/kogai/meerkats-hear-you/pull/53) がこれを `AppDelegate` の停止・再開の経路に載せる。

## 決定

### 1. 音のスレッドがするのは、写すことだけ。ロックは取らない

音のスレッドは、事前に確保しておいたリングへサンプルを写し、時刻を添えて、戻る。
確保もSQLiteも時刻の整形もしない。

**リングは単一生産者・単一消費者とし、添字はアトミックに持つ。** 音のスレッドでロックを取ると、
記録側が握っている間そこで待つことになり、この決定が何もしないのと同じになる
(`PipelineBox` の `NSLock` は優先度継承を持たない)。
消費者を起こす手段も、確保を伴わないものに限る。

### 2. 溢れたら、**新しいほう**を捨てる

古いほうを捨てる形にすると、生産者が消費者の読んでいるスロットを上書きする。
単一生産者・単一消費者のリングが成り立たなくなる。

### 3. 捨てたぶんは時刻を進め、空隙として記録する

捨てたサンプルのぶんだけフレーム番号を進める。進めないと、**タイムラインが恒久的に縮む。**

そのうえで、捨てた区間を理由つきで残す。黙って捨てると、記録は「その間は静かだった」と読める。
空隙の持ち方そのものは [ADR-0015](0015-frame-count-with-clock-resync.md) で提案中である。
捨てた区間を残すという要求はそれとは独立に立つが、**置き場所はそちらの決定に従う。**

### 4. リングは可変長のペイロードを扱う

48kHz・100ms・Float で1バッファ 19,200バイトになる。これを固定スロットにすると、
バッファの短い経路では大半が無駄になり、逆にこれを超えるバッファが来たときには黙って落ちる。
長さは実測で決めてよいが、**固定スロットにしないことは決定事項とする。**

### 5. 記録のキューはストリームごとに1本

パイプラインの状態はストリームに閉じているので、共有する理由がない。
共有すると、2本のうち片方が詰まったときにもう片方も止まる。
**しかも2本は同じ瞬間に異常へ入る。** 相手の声が途切れれば、こちらも聞き返して黙る。
詰まるときに揃って詰まる形になる。

接続は1本のままでよい。上で訂正したとおり、FULLMUTEX の待ちはAPI呼び出し単位で短い。

### 6. 終了時は、キューを同期に待つ

待たずに閉じると、溜まっている常時層——最大で `flushIntervalSeconds` ぶん、いまは10秒——が
毎回消える。終了のたびに末尾10秒が欠ける記録になる。

### 7. 自動チェックポイントを切り、記録の谷間で明示的に打つ

`PRAGMA wal_autocheckpoint = 0` にして、COMMIT の中でチェックポイントが走らないようにする。
チェックポイントは記録キューの上から明示的に呼ぶ。

分析ウインドウの読み出しは別接続で開く。ただし**読み手がいる間はチェックポイントが進まない**
(読み手が WAL の read-mark を持つため)。ウインドウを長く開いたままにするとWALが伸びるので、
ウインドウを閉じたときにも一度打つ。

## 確かめること

- チェックポイント1回の実費用。音の途切れとして現れる長さかどうか。
  **fsync の実装に依るので、これだけは実機でしか測れない**(macOS の `F_FULLFSYNC` は
  他のプラットフォームの fsync と挙動が違う)。頻度のほうは上記のとおり実測済み
- リングの長さ。何msぶん抱えれば溢れないか

いずれもこの環境では測れない。実機スパイクに回す。

## 影響

- 記録は、音が届いてから書かれるまでにキューぶんの遅れを持つ。常時層はもともと10秒まとめ書きなので、
  振り返りには影響しない。常時表示(`LiveState`)も同じ遅れを持つが、1秒粒度の表示に対しては見えない。
- `SystemOutputTap` に `PipelineBox` 相当の境界が要る。この決定はそれを前提にしている。
- 接続が2本になる。書き手が1本、読み手が1本で、WALの想定どおりの使い方になる。
- テストからはキューを同期に回せる形にする必要がある。いまの `RecordingPipeline` のテストは
  `ingest` を直に呼んでいるので、そこは変わらない。変わるのは繋ぎ込み側だけである。
- IOスレッドから確保と書き込みを外す作業は、この決定の実装で閉じる。

### ADR-0015(提案中)との関係

時刻は**音のスレッドで採り、リングに載せて渡す。**

ADR-0015 は、途切れたと分かった時点で連続単調時計を読み、それを新しい基準にする。
その読みが**捌かれた時刻**だと、キューに溜まっていたぶんだけ基準が後ろへずれる。
記録される空隙が、実際より長くなる。

キューが詰まるのは、まさに機械が苦しいときである。**取りこぼしがいちばん起きやすいときに、
その長さをいちばん大きく間違える。**

## 検討した代替案

### いまのまま(FULLMUTEX に任せる)

**採用しない。** 接続は壊れないが、チェックポイントのfsyncと詳細層のBLOB書き込みが
音のスレッドで走る。どちらも分析ウインドウとは無関係に起きる。

### `AudioDeviceCreateIOProcIDWithBlock` にディスパッチキューを渡す

Core Audio 側に非同期化させる手で、insidegui/AudioCap がこの形を採っている。**いまは採らない。**

渡されたバッファの寿命が、非同期に回されたあとも保つのかを確かめられていない。
確かめずに変えれば use-after-free を仕込むことになり、しかもそれは音のスレッドで
散発的に落ちる形で現れる。いちばん追いにくい壊れ方である。

加えて、この手はCore Audio側の経路にしか効かない。マイク側は AVAudioEngine の
`installTap` なので同じ手が使えない。2つの経路に理由の違う実装が並ぶことになる。

### スレッドごとに接続を開く

WALなら複数の書き手を持てる。**採用しない。**

書き手が2本になると、ミューテックスでの短い待ちが `SQLITE_BUSY` の再試行に変わる。
FULLMUTEX の待ちが短いと分かった以上、取り換える理由がない。

### 記録のキューを1本にして2本のストリームで共有する

この ADR の最初の版がこれだった。**採用しない。**

当時の理由は「別々にするとSQLiteのミューテックスで待ち合う」だったが、
**その理由は成り立たない。** 待ちは記録キューの上にあり、そこで直列化される。
実在する代償はヘッドオブラインのほうで、決定5に書いたとおり2本は相関して詰まる。

### 常時層の書き込み間隔を伸ばす

**採用しない。** 頻度が下がっても、1回あたりの書き込みは長くなる。
WALに積まれる総ページ数は変わらないので、チェックポイントの間隔も変わらない。
詳細層は常時層の間隔と無関係なので、(b) には何も効かない。

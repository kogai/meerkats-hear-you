# ADR-0016: 音のスレッドは値を渡すだけにし、記録は専用のスレッドで書く

## ステータス

Proposed (2026-09-13)

## 背景

いま、SQLiteへの書き込みは音のスレッドから起きている。

```
AudioCapture.handle / SystemOutputTap.handle   ← 音のスレッド
  → RecordingPipeline.ingest
    → sink.write(seconds:)                     ← 10秒に1回
      → RecordingStore.appendSeconds           ← SQLite
```

`Array(UnsafeBufferPointer(...))` による確保と `Date()` も同じ場所にある(#10)。

**音のスレッドで時間を使うと音が途切れる。記録しようとしている当の現象を、この道具が自分で作る。**

### 接続の直列化は既にある。壊れるのはそこではない

先に訂正しておく。接続は `SQLITE_OPEN_FULLMUTEX` で開いてある
(`RecordingStore.swift:31`)。同じ接続を複数のスレッドから呼んでもSQLiteが直列化するので、
接続が壊れるわけではない。

問題はその直列化の**待ち方**にある。

分析ウインドウは `store.seconds(streamId:)` をメインスレッドから同期に呼び、
そのストリームの全行を読む(`AnalysisWindow.swift:36`)。常時層は1秒1行なので、
8時間のセッションなら1ストリームあたり約29,000行になる。この読み出しが走っている間、
接続のミューテックスは握られたままで、**音のスレッドはそこで待つ。**

利用者が「聞こえにくかった」と思って分析ウインドウを開いたそのときに、
音のスレッドが止まる。いちばん開かれる瞬間に、いちばん起きてほしくない形で起きる。

### `close()` は守られていない

`RecordingStore.close()` は `sqlite3_close_v2` を呼んだあと `db` を `nil` にする。
この `db` は `var` で、音のスレッドから読まれている。FULLMUTEX が守るのはSQLiteの内部状態であって、
Swiftのプロパティではない。

いまは `applicationWillTerminate` が `capture?.stop()` を先に呼ぶので救われている。
救っているのは呼び出し順だけで、型が守っているものは何もない。
#53 が出力タップの停止と再開を足すと、この順序を守るべき経路が増える。

## 決定

### 1. 音のスレッドがするのは、写すことだけ

音のスレッドは、事前に確保しておいたリングバッファへサンプルを写し、
そのバッファが届いた時刻を添えて、戻る。確保もSQLiteも時刻の整形もしない。

### 2. 専用の直列キューが1本、リングを吸って記録する

`RecordingPipeline` と `RecordingStore` は、この1本のキューの上だけで触る。
2本のストリームは同じキューを使う。別々にすると、SQLiteのミューテックスで
待ち合うところへ戻ってしまう。`close()` もこのキューへ載せる。

キューが所有者になるので、`db` を読むスレッドは1本になる。
呼び出し順で守っていたものが、置き場所で守られる。

分析ウインドウの読み出しは**別の接続**で開く。WALなので、書き手を止めずに読める。
これがないと、キューを分けても分析ウインドウが音のスレッドを止める経路が残る
——正確には、キューを分けたことで止まるのが音のスレッドから記録キューへ移るだけになる。

### 3. 時刻は音のスレッドで採り、リングに載せて渡す

これは [ADR-0015](0015-frame-count-with-clock-resync.md) の前提を壊さないために要る。

ADR-0015 は「バッファが届いた時刻」と「フレーム数から決まる時刻」を比べて継ぎ直す。
キューの上で時計を読むと、それは届いた時刻ではなく**捌かれた時刻**になる。
キューが詰まっていれば遅れ、その遅れが継ぎ直しの判定に入る。
取りこぼしとキューの遅れが区別できなくなり、ADR-0015 の閾値が意味を失う。

`mach_continuous_time()` と `Date()` の読みは、リングの1要素に載せて渡す。

### 4. 溢れたら古い方を捨て、捨てたことを数える

リングが一杯になったときに音のスレッドを待たせては、目的が消える。古い方から捨てる。

**捨てた数は数え、記録に残す。** 捨てたことを黙っていると、記録は「その間は静かだった」と読める。
[ADR-0008](0008-process-tap-for-received-audio.md) が避けようとした「記録上は正常」を、
今度は自分の実装の都合で作ることになる。

リングの長さは、キューが数百ms止まっても溢れない程度に採る。具体値は実測で決める。

## 影響

- 記録は、音が届いてから書かれるまでにキューぶんの遅れを持つ。常時層はもともと10秒まとめ書きなので、
  振り返りには影響しない。常時表示(`LiveState`)も同じ遅れを持つが、1秒粒度の表示に対しては見えない。
- テストからはキューを同期に回せる形にする必要がある。いまの `RecordingPipeline` のテストは
  `ingest` を直に呼んでいるので、そこは変わらない。変わるのは繋ぎ込み側だけである。
- 接続が2本になる。書き手が1本、読み手が1本で、WALの想定どおりの使い方になる。
- #10 はこの決定の実装で閉じる。

## 検討した代替案

### いまのまま(FULLMUTEX に任せる)

**採用しない。** 上に書いたとおり、待たされるのが音のスレッドであり、
待たせるのが分析ウインドウの全行読み出しである。いちばん悪い組み合わせになっている。

### `AudioDeviceCreateIOProcIDWithBlock` にディスパッチキューを渡す

Core Audio 側に非同期化させる手で、insidegui/AudioCap がこの形を採っている。**いまは採らない。**

渡されたバッファの寿命が、非同期に回されたあとも保つのかを確かめられていない。
確かめずに変えれば use-after-free を仕込むことになり、しかもそれは音のスレッドで
散発的に落ちる形で現れる。いちばん追いにくい壊れ方である。

加えて、この手はCore Audio側の経路にしか効かない。マイク側は AVAudioEngine の
`installTap` なので同じ手が使えず、#10 が「片方だけ直さないこと」と書いた形になる。

### スレッドごとに接続を開く

WALなら複数の書き手を持てる。**採用しない。**

書き手が2本になると、ミューテックスでの待ちが `SQLITE_BUSY` に変わるだけである。
待ちが見えるようになる代わりに、再試行を音のスレッドで書くことになる。悪化している。

### 常時層の書き込み間隔を伸ばして、音のスレッドで書き続ける

**採用しない。** 頻度が下がっても、1回あたりの書き込みは長くなる。
音が途切れる回数が減って、途切れ方が派手になる。分析ウインドウとの競合は何も変わらない。

# ADR-0002: 記録はハイブリッド粒度で保存する

## ステータス

Accepted

## 背景

要望書は性質の異なる2つの用途を求めている。

1. 指摘されずとも、聞き取りづらくなっていたら気づける(リアルタイム)
2. 指摘されたら、どこがどのように聞き取りづらかったのか振り返れる(事後分析)

解析は20msフレーム単位で行う。これをそのまま保存すると毎秒50点、1時間で18万点になる。
一方で1秒に集約すれば1時間3600点まで落ちるが、要望書が問題視している「一瞬の音の途切れ」は
平均値に埋もれて消える。これは

> 聞き取りづらいと言われてるのに記録上は正常となると作る意味が皆無になる。

という、要望書が最も避けたい失敗そのものにあたる。

なお、振幅の包絡だけではスペクトル情報がないため発話内容は復元できない。記録から読み取れるのは
誰がいつ何秒話したかという発話タイミングにとどまる。したがって粒度の判断はプライバシーの問題ではなく、
保存量と分析解像度のトレードオフである。

## 決定

2層で保存する。

- **常時層** — 1秒ごとの集約値(平均レベル、最小レベル、最大レベル、発話フレーム比率、クリップ率)。
  最小レベルを持つことで、1秒の中に生じた瞬間的な落ち込みが平均に埋もれずに残る。
- **詳細層** — 異常を検知した区間の前後のみ、20msフレームの値をそのまま保存する。

詳細層の取得には、直近数秒分の20msフレーム値をメモリ上のリングバッファに保持し、異常検知時に
その内容を書き出す。これにより異常の「開始前」のフレームも残せる。

リングバッファが保持するのは各フレームから算出した値(レベル、発話判定、クリップ率)であり、
PCMそのものは保持しない。

## 影響

- 平常時の保存量は1時間あたり数百KB程度に収まり、長期保存が現実的になる。
- 振り返りたい箇所には20msの解像度が残るため、瞬間的な途切れを事後に確認できる。
- **生のPCMがディスクに書かれないことが、運用ルールではなく構造として保証される。** プロセスがPCMを
  保持するのはオーディオコールバックが渡す1フレーム分の間だけで、それ以降はレベル等の派生値しか残らない。
  要望書の「復元もできないのがよい」という要件は、この構造によって満たされる。
- **異常検知のトリガー条件が、記録内容そのものを左右するようになる。** トリガーが鈍ければ、後から見たい
  箇所に詳細層が残っていないという事態が起こりうる。トリガー条件は実運用しながら調整する前提が必要。
- 実装は単層保存より複雑になる(リングバッファ、トリガー判定、2種類のレコード)。
- **20msフレームは、OSから届くバッファをそのまま使うのではなく、自前で切り直して作る必要がある。**
  [スパイクの実測](../experiments/macos-app-bundle-spike-result.md)では、AVAudioEngineのタップに
  1024サンプル(48kHzで約21ms)を指定しても、実際には約100msのバッファが届いた。`bufferSize` は
  ヒントにすぎず、実際の長さはデバイス側の都合で決まる。バッファ長に依存して設計すると、
  デバイスが変わるたびに記録の粒度が変わってしまう。

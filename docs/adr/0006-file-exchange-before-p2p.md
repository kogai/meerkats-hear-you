# ADR-0006: 突合は初期版ではファイル交換で行い、P2Pは後回しにする

## ステータス

Accepted (2026-09-11)

## 背景

要望書はデータのやり取りについてこう書いている。

> データのやり取りがどうしても必要なら、システムを迂回して人間に送ってもらうか、
> エージェント同士のP2Pにする。ただしP2Pでも暗黙に送ることはNG。

つまりファイル経由の受け渡しは、P2Pと並ぶ選択肢として明示的に許容されている。

P2Pを実装する場合、macOS同士であればNetwork.framework + Bonjourで同一LAN内の探索と接続がそのまま
書ける。ただし探索・接続・認証・転送の一式が必要になり、さらに「暗黙に送らない」ことを担保する
同意フローも別途要る。

### 1秒集約だけでは、整合精度は±0.2秒程度で頭打ちになる

[ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md)は、2台の記録に共通の信号が含まれることを
利用して、レベル時系列の相互相関でオフセットを実測できるとした。ではその精度はどれほどか。交換する
のが[ADR-0004](0004-sqlite-storage.md)の常時層(1秒集約)だけの場合を数値実験で確かめた
([`experiments/xcorr-alignment-resolution.py`](../../experiments/xcorr-alignment-resolution.py)、
`mise run xcorr` で再現できる)。

10分の記録、1秒ごとの発話比率のみを交換、相手側は利得もノイズも異なるという条件で、相関ピークを
放物線補間した結果は次のとおり。

| 真のずれ | 誤差の平均 | 誤差の標準偏差 | 最大誤差 |
|---:|---:|---:|---:|
| 0.0s | 0.000s | 0.001〜0.011s | 0.022s |
| 0.3s | **-0.153s** | 0.009〜0.021s | 0.195s |
| 0.5s | -0.004s | 0.033〜0.075s | 0.187s |
| 1.7s | **+0.152s** | 0.008〜0.020s | 0.177s |

補間を入れない(整数ラグのみ)場合、0.3秒のずれは誤差0.300秒、つまり「ずれなし」と判定されてしまう。
補間には明確な効果があり、最大誤差は0.5秒から0.2秒程度に縮む。

ただし**0.15秒ほどの系統的な偏りが残る。** 1秒への集約が矩形窓の平均であり、理想的な帯域制限に
なっていないためである。0.3秒のずれは0.147秒と推定され、真値へ寄らない。

したがって**1秒集約のみの交換で得られる整合精度は±0.2秒程度が限界**である。しかもこれは、両者が
同一の包絡を共有するという理想的な条件での数値であり、実データでは各種の処理が挟まる分これより
悪くなる。

秒単位で起きる事象(数百msから数秒の音切れ)の対応づけには足りるが、それより短い現象を正確に
突き合わせることはできない。**交換形式は、必要に応じてより細かいデータを載せられる必要がある。**

### 送る中身が読めることには意味がある

要望書はプライバシーについて踏み込んで書いており、暗黙の送信を禁じている。この文脈では、
**利用者が渡す前に中身を自分で確認できる**ことが、単なる利便性ではなく要件に直結する性質になる。
バイナリ形式は不透明であり、「音声レベル以外のものが入っていない」ことを利用者自身が確かめられない。

## 決定

初期版では、記録の指定範囲をファイルに書き出し、利用者が任意の手段で相手に渡し、相手のアプリが
それを取り込む方式とする。P2Pは後続の最適化として扱う。

- **形式はJSON**とする。利用者が開いて中身を読めることを優先する。
- **書き出すのは指定した時間範囲のみ**とし、記録全体は渡さない。
- 内容は以下とする。
  - 形式のバージョン(アプリ間の取り決めであるため)
  - ストリームの素性(`kind`、デバイス名、サンプルレート、フレーム長、エージェントのバージョン)
  - [ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md)の実時刻アンカー(整合の初期推定に使う)
  - 常時層の1秒集約値
  - **任意で、詳細層の区間**。上記のとおり1秒集約だけでは±0.2秒程度が限界のため、細かい突合が
    必要な場面ではこれを含められるようにする。

## 影響

- 初期版にネットワーク関連のコードが一切入らない。実装量と、考慮すべき障害モードが大きく減る。
- **「暗黙に送ることはNG」という要件が構造的に満たされる。** 書き出しも受け渡しも利用者の明示的な
  操作でしか起きず、アプリが自発的に通信する経路そのものが存在しない。
- JSONであるため、利用者は渡す前に中身を確認できる。**音声レベル以外が入っていないことを、実装を
  信用せずに自分で確かめられる。**
- 範囲を限って書き出すため、突合のために1日分の記録を丸ごと渡す必要がない。
- **整合精度の上限が±0.2秒程度であることを、分析側は前提にしなければならない。** これより細かい
  対応づけを示すことは、根拠のない精度を示すことになる([ADR-0003](0003-monotonic-clock-with-wall-clock-anchor.md)
  で時刻を不確かさ付きの区間として扱うと決めたのはこのためでもある)。
- **突合のたびに手作業が発生する。** 頻繁に突合するようになれば負担になり、その時点がP2Pを導入する
  判断点になる。
- JSONは同じ内容のバイナリ形式より嵩む。1時間分の常時層で数百KB程度であり、受け渡しに支障はない。

## 検討した代替案

### SQLiteファイルをそのまま渡す

変換処理が要らない。採用しないのは、渡す範囲を限定できないこと(記録全体が入る)と、利用者が中身を
確認しにくいことによる。どちらもプライバシー上の要件に直接反する。

### バイナリ形式

同じ内容をより小さく運べるが、利用者が中身を確認できなくなる。この用途では嵩よりも読めることのほうが
重要である。1時間で数百KBという規模では、圧縮する動機も薄い。採用しない。

### 最初からP2Pにする

突合のたびの手作業がなくなる。ただし探索・接続・認証・転送に加えて「暗黙に送らない」ための同意フローが
必要になり、初期版としては重い。ファイル交換で実際の運用感を掴んでから判断するほうが、必要な同意フローの
形も見えやすい。採用しない(後続の最適化として残す)。

# 検証レポート: サンプル時刻の連続性と、未知の取りこぼしの検出

実施: 2026-09-24(Mac実機) / スパイク: [`experiments/sample-time-continuity`](../../experiments/sample-time-continuity/)
生の出力: [1回目](https://github.com/kogai/meerkats-hear-you/pull/64#issuecomment-5805304670) /
[2回目](https://github.com/kogai/meerkats-hear-you/pull/64#issuecomment-5805555516)

## 1. 目的

[ADR-0015](../adr/0015-frame-count-with-clock-resync.md) は、**途切れたと分かっている事象**でだけ
記録の基準を打ち直すと決めた。知らない場合が1つ残る。**エンジンが走ったまま、過負荷で
バッファが飛んだとき**である。こちらの知っている事象は何も起きないので、打ち直しも空隙の記録も
起きず、**取りこぼした区間が記録の上では「静かだった」と読める。**

拾える見込みがあるのは音声層が報告するサンプル時刻の不連続だけで、それが実際に取れるかを
確かめていなかった。確かめたのは次の3つ。

1. `AVAudioTime` からサンプル時刻が取れるか。取れるとして連続しているか
2. バッファを落としたとき、サンプル時刻の飛びとして現れるか
3. ホストタイムが `mach_absolute_time` と `mach_continuous_time` のどちらの基数か

3つ目は [ADR-0003](../adr/0003-monotonic-clock-with-wall-clock-anchor.md) が連続単調時計を
指定しているために要る。中断側の基数なら、連続側へ移す手当てが要る。

## 2. 実行環境

マイク入力 48000 Hz / 1ch。`installTap(bufferSize: 1024)` に対し、**実際に届くバッファは
4800 フレーム(100ms)固定**。タイムベースは 24MHz(1バッファあたり 2,400,000 刻み)。
実装側 `AudioCapture.swift` の「bufferSize はヒントにすぎず、実測では約100msのバッファが届く」と
一致する。

過負荷は**タップの閉包の中で寝ること**で作った。実装でも記録を書いているのはこの閉包なので、
ここが詰まることがそのまま過負荷の形になる。

## 3. 結果

### 3.1 サンプル時刻は取れる。連続している

`isSampleTimeValid` / `isHostTimeValid` とも、2回の実行(149バッファ / 270バッファ)を通じて
全バッファで true。`frameLength` は 4800 固定。詰まらせていない区間では、サンプル時刻は
バッファ長ちょうどずつ進む。

### 3.2 落ちたぶんは、サンプル時刻の飛びとして現れる

2回目(40秒の窓、1秒・4秒・12秒の3回の詰まらせ)。

| 詰まらせ | 飛び | 落ちた長さ | 追いつきの束 |
|---|---|---|---|
| 1.0 秒 | なし | 0 秒 | 直後に9バッファ |
| 4.0 秒 | 120,000 サンプル | **2.500 秒** | — |
| 12.0 秒 | 504,000 サンプル | **10.500 秒** | — |

勘定は閉じている。受け取った音声 27.000 秒 + 飛び 13.000 秒 = **40.000 秒**(サンプル時刻の
張る幅)で、到着から見た窓は 39.993 秒。**差は -0.007 秒**で、どこにも現れていない取りこぼしは無い。

**ホストタイムも同じ空きを示す。** 飛びの前後で `hostTime` の差からバッファ1つぶんを引くと、
2.5000 秒 と 10.4999 秒。サンプル時刻の飛び(2.500 / 10.500 秒)と一致する。
音声層の2つの時刻が独立に同じことを言っている。

### 3.3 タップは約1.5秒ぶん抱える

落ちなかったぶんが、そのまま抱えられる量になる。

| 詰まらせ | 落ちた | 抱えられた |
|---|---|---|
| 1.0 秒 | 0 秒 | 1.0 秒(全部) |
| 4.0 秒 | 2.5 秒 | **1.5 秒** |
| 12.0 秒 | 10.5 秒 | **1.5 秒** |

3点が一致するので、**AVAudioEngine のタップは約1.5秒ぶん溜めてから捨てる。**
1.0 秒が無傷だったことも、この値と矛盾しない。

### 3.4 ホストタイムは中断側の基数

到着時に読んだ時刻との差。

| | 1回目 | 2回目 |
|---|---|---|
| `mach_absolute_time` - `hostTime` | +103.229 ms | +101.851 ms |
| `mach_continuous_time` - `hostTime` | +808,717,270.228 ms | +808,717,268.850 ms |

絶対時刻との差はバッファ1つぶん(100ms)+ 2〜3ms で、`hostTime` がバッファ先頭を指していることと
整合する。連続時刻との差は **9.36日**あり、これは起動以降のスリープの累計である。

**この機械はスリープを挟んでいるので、判定は成立している。** `AVAudioTime.hostTime` は
`mach_absolute_time` の基数であり、**スリープ中は止まる。**

## 4. 予測との突き合わせ

- **当たった:** サンプル時刻で未知の取りこぼしを拾えるという ADR-0015 の見込み。3.2 のとおり
- **外れた:** 「詰まらせれば落ちる」という 1回目の設計。0.8秒では**何も落ちなかった**
  (149バッファ = 14.900秒、窓は15秒)。3.3 の 1.5秒に届いていない

## 5. 1回目の誤り

**1回目のスパイクは、取りこぼしの有無を数えていなかった。** そのため「飛びなし」を
*落ちたのに見えない*と読み、「この手では拾えない」という結論を出力した。実際には
*落ちていない*のであって、**結論は逆に近い。**

数えていれば1回目で分かったことなので、作りの誤りである。2回目では、到着から見た窓の長さと
サンプル時刻が張る幅を突き合わせ、結論を3つ(飛びが出た / 飛びは無いが勘定が合わない /
そもそも落ちていない)に分けた。

## 6. 他の決定への影響

- **ADR-0015 決定2の4つ目が確定した。** サンプル時刻の不連続を打ち直しの契機にできる。
  `RecordingGap.Reason` に1つ足して実装に入る
- **ADR-0003 に補足が要る。** `AVAudioTime.hostTime` は中断側なので、連続単調時計へ移すには
  到着ごとに両方を読んで差を取る
- **[ADR-0016](../adr/0016-handoff-off-the-audio-thread.md) の「リングの長さ」に数字が1つ付いた。**
  タップの経路は約1.5秒ぶん抱える。**リングがこれより短ければ、溢れるのはリングが先になる。**
  ADR-0016 はリングの長さを実機スパイクに回しているが、上限の目安はここで出た

## 7. 未検証のまま残るもの

- **2本のストリームのサンプル時刻が同じ基数に乗っているか。** このスパイクはマイク側だけを見た。
  受信側(Core Audio のプロセスタップ)を足したときに確かめる。ADR-0012 の突合に効く
- **実装が実際に空隙を記録できるか。** ここで確かめたのは音声層が情報を出すことまでで、
  実装はまだその引数を捨てている(`AudioCapture.swift` の `{ buffer, _ in }`)

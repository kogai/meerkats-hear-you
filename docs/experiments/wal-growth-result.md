# WALが自動チェックポイントの閾値に達するまで

2026-09-13 / `experiments/wal-growth/measure.py`

## 何を測ったか

[ADR-0016](../adr/0016-handoff-off-the-audio-thread.md) は「WALの自動チェックポイントが
COMMIT の中、つまり音のスレッドで走る」ことを問題にしている。`PRAGMA wal_autocheckpoint`
の既定は1000ページで、そこに達するまでの時間は**1コミットあたりWALに積まれるページ数**で
決まる。ADR を書いた時点では「1ストリームで1時間前後」という見積もりだった。

これはスキーマと行の大きさで決まるので、**macOS でなくても測れる。**
エージェントと同じスキーマ・同じ書き込みパターンをこの環境で再現した。

- 常時層 `seconds` を1秒1行、`flushIntervalSeconds`(10秒)ごとに1トランザクション
- 詳細層 `detail_windows` は異常に入るたび1行。BLOB は 500フレーム × 5バイト
- アンカーは5分に1行
- `page_size = 4096`、`journal_mode = WAL`、`synchronous = NORMAL`

測定中は `wal_autocheckpoint = 0` にしてある。切らないと1000ページで勝手に畳まれ、
「1000ページに達するまで」を測っているつもりが畳まれた後の量を見ることになる。

## 結果

| ストリーム | 詳細層 | 1000ページ到達 | 1コミットあたり |
|---|---|---|---|
| 1本 | なし | 57分20秒 | 2.91ページ |
| 1本 | 5分に1回 | 55分0秒 | 2.91ページ |
| 1本 | 1分に1回 | 49分0秒 | 2.92ページ |
| 2本 | なし | **26分40秒** | 3.24ページ |
| 2本 | 5分に1回 | 25分40秒 | 3.24ページ |
| 2本 | 1分に1回 | **23分0秒** | 3.21ページ |

## 読み取れること

**ADR-0016 の見積もりは当たっていた。** 1ストリームで約1時間、2本でその半分。
ここは断定に書き換えてよい。

**2本にすると半分より短くなる。** 1コミットあたりのページ数が 2.91 → 3.24 に増える。
2本の行が交互に入って、触る葉ページが増えるためである。単純に倍のペースではない。

**詳細層の寄与は小さい。** 1分に1回という最悪に近い頻度でも、1本で 57分 → 49分、
2本で 26分40秒 → 23分にしかならない。ADR-0016 は詳細層を
「頻度の高い中くらいのもの」として並べているが、**チェックポイントの頻度という面では
効いていない。** 効くのは書き込み1回の確保とBLOBのほうで、そちらは別の話である。

会議は1時間前後のことが多い。**2本走っていれば、会議1回のあいだに1〜2回は必ず当たる。**

## 測れなかったこと

**チェックポイント1回の実費用。** fsync の実装に依るので、この環境の数字は macOS の
参考にならない(macOS の `F_FULLFSYNC` は他のプラットフォームの fsync と挙動が違う)。
「何回起きるか」は出たが、「1回で何ms止まるか」は実機で測る必要がある。

止まる長さが仮に十分短ければ、ADR-0016 の (a) は優先度が下がる。
ただし (b) の詳細層の確保と (c) の毎バッファの確保は残るので、決定そのものは変わらない。

## 再現

```
mise run wal-growth
```

# 検証レポート: 受信音声の初回実機起動

実施: 2026-09-26(Mac実機、ad-hoc署名の `.app` バンドル)

## 1. 目的

`SystemOutputTap` を `main.swift` から起こしたので([#77](https://github.com/kogai/meerkats-hear-you/pull/77))、
**[ADR-0008](../adr/0008-process-tap-for-received-audio.md) の中心の前提——プロセスタップで
このMacの出力が取れること——を実機で確かめる。** これまで確かめていたのはコンパイルと
テストまでで、タップが音を拾うかは一度も見ていない。

## 2. 実行環境

- 出力・入力とも `Jabra Engage 50 II`
- `./build.sh`(`SIGN_IDENTITY` なし = ad-hoc)で作った `.app` を `open` で起動
- 2セッション。1回目は音を鳴らさず、2回目は音を鳴らした

## 3. 結果

### 3.1 タップは音を拾う

音を鳴らした区間(2セッション目の 57〜64 秒)の受信側。

| 秒 | mean_dbfs | max_dbfs |
|---|---|---|
| 57 | -18.0 | -10.3 |
| 58 | -16.6 | -10.3 |
| 59 | -16.1 | -10.5 |
| 60 | -17.0 | -10.4 |
| 61 | -16.2 | -9.6 |
| 62 | -18.5 | -11.8 |
| 63 | -16.9 | -10.2 |
| 64 | -15.4 | -9.8 |

**ADR-0008 の前提は成立する。** 集約デバイスのサブデバイス一覧が空でも、タップだけを
載せた集約で音が取れている。

### 3.2 記録されたストリーム

```
id  session_id  kind    device_name         sample_rate  frame_ms
1   1           mic     Jabra Engage 50 II  48000        20
2   1           output                      48000        20
3   2           mic     Jabra Engage 50 II  48000        20
4   2           output                      48000        20
```

- **2本とも 48000 Hz / 20ms。** 率が揃っているので、突合で率を合わせる手当ては要らない
- **受信側の `device_name` は空。** 意図どおり(ADR-0013。プロセスタップが拾うのは
  このMacの出力そのもので、利用者が選んだ機器ではない)

### 3.3 許可

**ダイアログは2つ出た。** マイクと、音声取り込み。ad-hoc署名の新しいバンドルなので、
過去に `swift run` で走らせたスパイク(許可はターミナルに付く)とは別に求められた。

その待ち時間が `gaps` に残っている。

| ストリーム | reason | 長さ |
|---|---|---|
| mic | start | 10.311 秒 |
| output | start | 12.614 秒 |

**記録は開始しているが最初のバッファが来ていない区間**として残る形で、
ADR-0015 決定2 の打ち直しが実際に動いている。

### 3.4 終了

`sessions` の `ended_wall_us` が2セッションとも入っており、`pgrep` でプロセスは残っていない。
**メニューの「終了」から `applicationWillTerminate` を通って締められている。**

### 3.5 無音は無音として記録された

1セッション目は受信側が 58 行すべて -90.0 dBFS(下限)。**これは何も鳴らしていない
区間なので正しい。** ADR-0013 が懸念する「タップが死んでゼロを返し続ける」状態とは
区別が付いている——2セッション目で同じ構成のタップが音を拾っているため。

## 4. 予測との突き合わせ

**外した。** 1セッション目の -90.0 を見た時点で、集約デバイスの
`kAudioAggregateDeviceSubDeviceListKey` が空であることを原因と見立てた。**音を鳴らして
測り直したら値が動いたので、原因は「何も鳴っていなかった」だった。**
構成を疑う前に、入力があったかどうかを先に確かめるべきだった。

## 5. 未解決のまま残るもの

- **1セッション目の記録が 4.459 秒ぶん足りない。** 実時間 62.459 秒に対して受信側 58 行
  (2セッション目は 65.435 秒に対して 65 行で、差は 0.435 秒)。`gaps` の `start` が
  12.614 秒あることと合わせると勘定が合わない。**どこが抜けているのかを追っていない。**
- **メニューバーの表示を確認していない。** 2ブロック出ているか、許可前に
  「まだ測れていない」が出ていたかを見ていない
- **長時間張りっぱなしのタップ**(ADR-0013)。今回は最長 65 秒
- **2本のサンプル時刻が同じ基数に乗っているか**(ADR-0012 の突合)。今回は見ていない
- **受信側の閾値**(ADR-0008)。会議アプリを鳴らしたときのレベル分布を取っていない。
  今回鳴らしたのは会議の音ではない

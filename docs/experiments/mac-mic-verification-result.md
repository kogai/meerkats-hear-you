# 検証レポート: Mac実機でのマイク音声レベル/発話区間検出

対象要望書: [`docs/requirements/audio-level-monitoring.md`](../requirements/audio-level-monitoring.md)
使用ツール: [`experiments/mac-mic-verification/`](../../experiments/mac-mic-verification/)
実行日時: 2026-09-11 19:15:30

## 1. 目的

要望書の実現にあたり、まず「発話・音声レベルの検知」が実機で成立するかを確認する。
具体的には以下3点を、実際のMac・実際のマイクで確かめる。

1. 追加のネイティブインストールなしに、マイク入力をキャプチャできるか。
2. 音声レベル(dBFS)と発話区間(VAD)が、妥当な値として取得できるか。
3. 正常な録音条件で誤って異常判定を出さないか。

## 2. 実行環境

| 項目 | 値 |
|---|---|
| OS | macOS 26.5.1 (arm64 / Apple Silicon) |
| Python | 3.12.14 (mise管理) |
| キャプチャ | `sounddevice` (PortAudio) |
| VAD | `webrtcvad`(利用可) + 依存なしの適応的エネルギー閾値方式 |
| 録音条件 | 16kHz / mono / 15秒 / システム既定の入力デバイス |

検出された入力可能デバイスは4件(Jabra Engage 50 II、HD Pro Webcam C920、MacBook Proのマイク、
および入出力兼用の2件)。

## 3. 結果

| 指標 | 値 |
|---|---:|
| 全体レベル | -27.27 dBFS |
| ノイズフロア(推定) | -61.71 dBFS |
| 発話区間の平均レベル(エネルギーVAD基準) | -26.06 dBFS |
| 発話区間の平均レベル(WebRTC VAD基準) | -26.52 dBFS |
| 非発話区間の平均レベル | -59.25 dBFS |
| 推定SN比 | 33.19 dB |
| クリッピング率 | 0.00% |
| 発話区間比率(エネルギーVAD) | 75.7% |
| 発話区間比率(WebRTC VAD) | 84.1% |
| 2方式のVAD一致率 | 90.8% |
| 自動判定フラグ | NORMAL(明確な異常は検出されず) |

## 4. わかったこと

### 4.1 実機でのキャプチャは追加インストールなしに成立した

`pip install sounddevice` のみで、Homebrew等でのPortAudioの別途インストールを必要とせず、
Apple SiliconのmacOS上でマイクキャプチャが動作した。`webrtcvad`(WebRTC由来のVAD)も
arm64環境でそのまま導入・実行できた。**マイク入力側については、環境構築の障壁は事実上ない**と言える。

### 4.2 レベル計測値は妥当で、VADの選択に左右されない

発話レベルは-26 dBFS前後、ノイズフロアは-61.7 dBFS、推定SN比33.2 dBと、良好なマイク環境として
自然な値が得られた。クリッピングもゼロ。

特筆すべきは、**2つの独立したVAD方式が算出した発話レベルの差が0.46 dBに収まった**点
(-26.06 dBFS vs -26.52 dBFS)。要望書が求めている記録の本体は「音声レベル」であり、
その値がVADアルゴリズムの選択にほとんど影響されないことは、記録の安定性という意味で好材料となる。

### 4.3 2方式のVADの差の出方には傾向がある

発話区間比率はエネルギーVADが75.7%、WebRTC VADが84.1%で、WebRTC VADのほうが約8ポイント多く
発話と判定した(一致率90.8%)。かつWebRTC VAD基準の平均レベルのほうが0.46 dB低い。
つまり**WebRTC VADが追加で拾っているフレームは、エネルギー閾値を下回る低レベルの音声**
(語頭・語尾の立ち上がり、息継ぎ混じりの発話など)であると考えられる。
固定マージン(+12 dB)のエネルギー閾値方式は、こうした低レベル発話を取りこぼす。

### 4.4 正常条件で誤検知は出なかった

良好な録音条件に対して判定は`NORMAL`であり、誤って異常フラグを立てることはなかった。

## 5. コンセプトは成立したと言えるか

**自分側エージェントについては、成立したと判断してよい。**

今回示されたのは「OSレベルで、特別なドライバや追加インストールなしに、会議アプリが使うのと同じ
入力を観測し、安定した音声レベル記録と発話区間を取り出せる」ということであり、これが要望書の
言うエージェント部分のコンセプトそのものである。

なお、意図的に劣化させた条件(音量を下げる、マイクから離れる等)でフラグが変わるかは今回試していないが、
これは実現可能性の問題ではなく閾値のチューニングの問題である。レベル記録が取れている以上、
入力レベルが下がれば記録はそのとおり下がる。検証の優先度は高くない。

### 残るギャップ: 「自分が何を出したか」と「相手に何が届いたか」は別物

この記録が示すのは**自分のマイクが拾った音**であって、**相手に届いた音**ではない。
要望書が挙げる

> 聞き取りづらいと言われてるのに記録上は正常となると作る意味が皆無になる。

という失敗は、マイク入力が正常でも、その下流(会議アプリのノイズ抑制・AGC・コーデック、および
ネットワーク)で劣化すれば起こりうる。そしてその劣化は、手元のマイク入力の記録には原理的に写らない。

これは今回の検証の不備ではなく、**コンセプトの残り半分**である。要望書が当初から
「発話と相手側の聞こえ方を突合出来るようにもしたほうがいいだろう」と書いているのは、
まさにこの構造的な理由による。この部分の検証は次ステップとして保留中。

## 6. ツール側に見つかった不備

### 6.1 ループバック候補デバイスの検出漏れ

`loopback_candidates` が空と報告されたが、デバイス一覧には入出力を兼ねる以下の2件が存在する。

| index | デバイス名 | in | out |
|---:|---|---:|---:|
| 6 | Speaker Audio Recorder | 2 | 2 |
| 7 | ZoomAudioDevice | 2 | 2 |

現在の検出はデバイス名のキーワード照合(blackhole/soundflower/loopback等)で行っているため、
これらを取りこぼした。**入力チャンネルと出力チャンネルを両方持つことが仮想オーディオデバイスの特徴**であり、
名前ではなくこの構造で判定すべきだった。ループバック側の検証は次ステップとして保留中だが、
その際にはこの判定ロジックの修正が前提になる。

### 6.2 実際に使用した入力デバイスが記録されていない(軽微)

`recording_device_index` は `null`(=システム既定を使用)としか記録されておらず、
4つある入力デバイスのうちどれで録音されたかが結果から判別できない。
解決済みのデバイス名を記録しておくと、後から記録を見返すときに条件を特定しやすい。

## 7. 結論

- マイク入力側の**音声レベル計測と発話区間検出は、Mac実機で問題なく成立する**。環境構築の障壁もない。
- 記録の本体である音声レベルは、VADアルゴリズムの選択に左右されない安定した値として取得できる。
- **自分側エージェントのコンセプトは成立したと判断してよい。**
- 残るのは「相手に何が届いたか」の側であり、これは要望書が当初から挙げていたコンセプトの残り半分にあたる。

## 8. 次のステップ(提案)

1. ループバック候補の検出ロジック修正(6.1)。入出力を兼ねるデバイスを候補とみなすよう変更する。
2. 相手側の聞こえ方(受信音声)の検証に着手する。`ZoomAudioDevice` のような会議アプリの仮想デバイス、
   または追加の仮想オーディオデバイス経由で、受信側の音声レベルを観測できるかを確かめる。

# NATの実挙動(実機・実回線)

[ADR-0009](../../docs/adr/0009-record-exchange-transport.md) が「未検証の前提」に
**NAT越えの実挙動**を残している。これを潰すためのスパイク。**普段使う回線で走らせる必要がある。**

## なぜ要るか

ADR-0009 は公開STUNで自分の公開アドレスを知り、keepaliveで保ち、両側から繰り返し送って
穴を開けると決めた。この形が成立するかは、**その回線のNATがどう振る舞うか**だけで決まる。

決め手は1つである。RFC 4787 の用語で、宛先が変わっても外側ポートが変わらないもの (EIM) と、
宛先ごとに変わるもの (EDM) がある。**EDM では穴あけが原理的に成立しない。**
ADR-0009 はそれを承知で「繋がらない相手が残る」と書き、ファイル書き出しを落とし所に残した。

知りたいのは、**その落とし所が例外なのか常態なのか**である。手元の回線が EDM なら、
本線の経路が最初から使えないことになり、ADR-0009 の方向そのものを見直すことになる。

keepalive の間隔も同じく測らないと決まらない。ADR-0009 は RFC 4787 が2分未満で切ることを
禁じている点を引きつつ、**30秒程度で切る実装が報告されている**ことも併記している。
どちらなのかで keepalive の間隔が変わる。

## 実行方法

```bash
mise run nat
```

または直接:

```bash
cd experiments/nat-behaviour
swift run NATBehaviourSpike
```

**3分強かかります。** 4節で黙って待つ時間がそのまま所要時間になります。

- 許可は要りません。音も出しません
- **普段オンライン会議をする回線で走らせてください。** VPN を繋いでいる場合は切ってください。
  VPN 越しに測ると、測れるのは VPN 事業者の出口の性質です
- テザリングでも走りますが、それは携帯網の性質であって自宅回線のものではありません。
  両方で走らせて結果が違えば、それ自体が知りたいことです

## 見るところ

**1. STUN が通るか** — 公開アドレスが出れば通っています。ここで止まるなら、UDP が塞がれて
いるか、STUN のポートが塞がれています。どちらでも ADR-0009 の本線は使えません。

「反射アドレスが自分のアドレスと同じ」と出たら、**その機械は NAT の内側に居ません。**
そのときの測定結果は普段の回線のことを何も言っていないので、別の回線で走らせてください。

**2. EIM か EDM か** — ここがいちばん知りたいところです。

- **EIM と出た** → 穴あけが成立する側。ADR-0009 の本線をそのまま実装に移せます
- **EDM と出た** → この回線では成立しません。ADR-0009 の「両側がEDMだと0.01%」に
  自分自身が入ります。**落とし所のファイル書き出しが主経路になります**

**3. ポートの振り方** — EDM だったときに効きます。ADR-0009 は誕生日のパラドックスによる
救済(両側が複数ポートを試す)を「後から足せる最適化」と書きました。外側ポートが連番で
振られているなら探索が要らず、その最適化の形が変わります。差が小さい整数なら連番です。

**4. マッピングの寿命** — keepalive の間隔がここで決まります。

- 180秒まで生きていた → RFC 4787 を守っている。ADR-0009 の想定どおり
- 30秒で切れた → **30秒より短い間隔で打ち続ける必要があります。** 常時起動の道具なので、
  相手ごとにこれが走ります。ADR-0014 の「喋っていないときは止める」と正面から衝突するので、
  そのときは ADR を1本書きます

## 測っていないこと

**穴あけそのものは測っていません。** 両端が要るので、1台では動かせません。ここで測るのは
片側のNATの性質だけです。両側の組み合わせで何が起きるかは、ADR-0009 が引いている実測
(DCUtR の440万回)に頼ります。

**フィルタの振る舞い(開いた穴が誰からのパケットを通すか)も測っていません。** RFC 5780 の
NAT Behavior Discovery が要りますが、公開STUNで対応しているものが少なく、確実に測るには
自前のサーバが2アドレス要ります。ランデブーを立てるときに一緒に足すのが筋です。

つまりこのスパイクは**「本線が成立しうるか」を1台で言える範囲で確かめるもの**で、
成立することの証明ではありません。EDM と出たときの否定のほうが確実です。

## この環境で確かめたこと

STUN の組み立てと読み取りは [RFC 5769](https://www.rfc-editor.org/rfc/rfc5769.html) の
公式テストベクタ(§2.2 の IPv4 応答、XOR-MAPPED-ADDRESS = 192.0.2.1:32853)に対して、
同じ手順を Python に写して突き合わせてあります。XOR あり・なしの両方の枝と、
トランザクションIDが食い違ったときに答えとして採らないことまで通しました。

**実際のサーバには当てていません。** この環境は UDP が出られないためです。
したがって通信の部分は実機で初めて走ります。
